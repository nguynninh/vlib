排版是每个文档页面的基础。在考虑表格、提示框或代码块之前，大部分内容仍然是标题、段落和基本的文本格式。

一个内容正确但排版混乱的页面——标题层级错误、粗体滥用、段落过长——仍然会让读者难以吸收信息。

例如，与其写一大段没有结构的文字：

```md title="没有结构"
安装该包需要运行 npm install，然后创建配置文件 config.json，重要的是必须填写正确的 API key，否则应用将无法启动。
```

不如将其拆分为清晰的标题、段落和行内代码。

---

## 1. 标题

标题用于对内容进行分级。在 Markdown 中，标题通过 `#` 创建，`#` 的数量对应标题的级别。

**代码**

```md showLineNumbers title="标题级别"
# 标题 1
## 标题 2
### 标题 3
#### 标题 4
```

在 Starlight 中，页面的 `title`（在 frontmatter 中声明）已经充当了一级标题。因此页面内容中应该从 `##`（二级标题）开始往下使用。

```mdx title="Frontmatter"
---
title: "页面名称"
---
```

:::caution[警告]
不要在 Starlight 的 MDX 内容中使用 `#`（一级标题），因为页面已经有自己的 title 充当一级标题。在内容中再加一个 `#` 会在同一页面产生两个一级标题，扰乱大纲结构和 SEO。
:::

### 标题顺序

标题应按照层级顺序依次使用，不应跳级。

不推荐：

```md title="跳过标题级别"
## 章节
#### 小节
```

这种写法直接从 `##` 跳到 `####`，跳过了 `###`。

推荐：

```md title="正确的标题顺序"
## 章节
### 小节
```

### 标题应简洁

好的写法：

```md
## 用户身份验证
```

不好的写法：

```md
## 该系统中用户身份验证的工作原理以及它为何重要
```

过长的标题会削弱目录（Table of Contents）的作用，因为读者难以快速扫读。

## 2. 段落

段落是普通的文本块，用一个空行与其他段落分隔。

**代码**

```md showLineNumbers title="段落"
这是第一段。

这是第二段。
```

**效果**

这是第一段。

这是第二段。

:::caution[警告]
如果两段之间没有空行，Markdown 会把它们合并成一个段落，而不是保留为两个独立的段落。
:::

### 段落应简短

在技术文档中，一个段落应专注于一个要点，通常不超过 3-4 句话。

不要把很多不同的要点写进一个很长的段落里。如果内容包含多个条目，应使用列表或表格，而不是硬塞进一个段落中。

---

## 3. 粗体

粗体用于强调重要的词语或短语，用两个 `**` 创建。

**代码**

```md showLineNumbers title="粗体"
调用此 API 时，`timeout` 参数是**必填**的。
```

**效果**

调用此 API 时，`timeout` 参数是**必填**的。

:::caution[警告]
不要在同一段落中对过多的词语使用粗体。如果所有内容都是粗体，就没有任何内容能突出显示，粗体也就失去了强调的作用。
:::

---

## 4. 斜体

斜体用一个 `*` 或 `_` 创建，通常用于术语、专有名词或轻微强调。

**代码**

```md showLineNumbers title="斜体"
在 Git 中，这个操作被称为 *rebase*。
```

**效果**

在 Git 中，这个操作被称为 *rebase*。

粗体和斜体可以用三个 `***` 组合使用。

**代码**

```md
这个警告***非常重要***。
```

**效果**

这个警告***非常重要***。

---

## 5. 删除线

删除线用两个 `~~` 创建，用于标记已过时或不再适用的内容。

**代码**

```md showLineNumbers title="删除线"
~~`getUserById`~~ 已被废弃，请改用 `findUserById`。
```

**效果**

~~`getUserById`~~ 已被废弃，请改用 `findUserById`。

---

## 6. 行内代码

行内代码用反引号 `` ` `` 创建，用于句子中出现的变量名、函数名、文件名、命令或技术性数值。

**代码**

```md showLineNumbers title="行内代码"
运行 `npm run build` 在 `dist/` 目录下生成文件。
```

**效果**

运行 `npm run build` 在 `dist/` 目录下生成文件。

以下情况应使用行内代码：

* 变量名、函数名、类名。
* 文件名、目录名。
* 终端命令。
* 具体的值（`true`、`null`、`200`）。
* 环境变量名称。

:::tip
如果一段行内代码本身需要包含反引号，可以用两个反引号将其包裹：`` `code` ``。
:::

---

## 7. 无序列表

无序列表用行首的 `-`、`*` 或 `+` 创建。

**代码**

```md showLineNumbers title="无序列表"
* 安装依赖。
* 配置环境。
* 执行迁移。
```

**效果**

* 安装依赖。
* 配置环境。
* 执行迁移。

:::tip
应只选择一种符号（`-`、`*` 或 `+`），并在整份文档中保持一致，以便源码更易读。
:::

### 嵌套列表

**代码**

```md showLineNumbers title="嵌套列表"
* 前端
    * React
    * Vue
* 后端
    * Node.js
    * Spring Boot
```

**效果**

* 前端
    * React
    * Vue
* 后端
    * Node.js
    * Spring Boot

嵌套列表每一级应缩进 4 个空格（或 1 个 tab），以避免解析器误判层级。

---

## 8. 有序列表

有序列表使用数字加 `.` 表示。

**代码**

```md showLineNumbers title="有序列表"
1. 克隆仓库。
2. 安装依赖。
3. 运行应用。
```

**效果**

1. 克隆仓库。
2. 安装依赖。
3. 运行应用。

:::note
Markdown 在渲染时会自动重新编号，所以即使你在源码中写 `1. 1. 1.`，渲染结果仍然是 `1. 2. 3.`。不过为了源码的可读性，仍建议写正确的序号。
:::

### 什么时候该用有序列表而不是无序列表？

| 场景                          | 列表类型 |
| ----------------------------- | :------: |
| 必须按顺序执行的步骤          | 有序     |
| 顺序不重要的列表              | 无序     |

如果改变条目的顺序会改变结果（例如安装步骤），应使用有序列表。

## 9. 任务列表

一些 Markdown 变体（包括 Starlight 支持的 GitHub-Flavored Markdown）允许在列表中使用复选框。

**代码**

```md showLineNumbers title="任务列表"
- [x] 编写 API 接口。
- [x] 编写单元测试。
- [ ] 编写文档。
```

**效果**

- [x] 编写 API 接口。
- [x] 编写单元测试。
- [ ] 编写文档。

任务列表适合用于进度检查清单，不应用来替代更复杂的状态表格。

## 10. 引用

引用用行首的 `>` 创建，用于引用或轻微强调一句话，其强调程度低于提示框（Callout）。

**代码**

```md showLineNumbers title="引用"
> `timeout` 定义了客户端在请求被判定为失败之前等待响应的最长时间。
```

**效果**

> `timeout` 定义了客户端在请求被判定为失败之前等待响应的最长时间。

### 引用与提示框有什么区别？

| 组件   | 用途                                       |
| ------ | -------------------------------------------- |
| 引用   | 引述、补充说明，不需要特别突出               |
| 提示框 | 需要吸引读者注意的警告或提示                 |

参见[提示框](/web-documentation/ui/callout)，了解何时应使用 `note`、`tip`、`caution` 或 `danger`，而不是引用。

引用可以用多个 `>` 嵌套。

**代码**

```md
> 原始引用内容。
>
> > 对该引用的补充评论。
```

**效果**

> 原始引用内容。
>
> > 对该引用的补充评论。

---

## 11. 水平分割线

水平分割线用单独一行的三个 `-`、`*` 或 `_` 创建，用于分隔较大的内容部分。

**代码**

```md
---
```

本文档使用水平分割线来分隔各个大的章节（`## 1.`、`## 2.`...），帮助读者更容易识别各部分之间的边界。

:::caution[警告]
如果在文件最开头、没有任何前置内容的情况下直接使用 `---`，一些 Markdown 解析器（包括 Astro/Starlight 的 frontmatter）可能会将其误判为 frontmatter 的边界。只应在 frontmatter 之后的正文中间使用 `---` 作为水平分割线。
:::

## 12. 链接

链接使用 `[文本](url)` 语法。

**代码**

```md showLineNumbers title="链接"
参见[表格](/web-documentation/ui/table)了解如何呈现表格数据。
```

**效果**

参见[表格](/web-documentation/ui/table)了解如何呈现表格数据。

### 内部链接与外部链接

| 链接类型 | 示例                                     |
| -------- | ----------------------------------------- |
| 内部     | `[表格](/web-documentation/ui/table)`     |
| 外部     | `[Astro](https://astro.build/)`           |

:::tip
对于内部链接，应使用站内相对路径（`/web-documentation/...`），而不是硬编码完整域名，这样在更换域名或在预发布环境运行时链接仍然有效。
:::

### 链接文字应清楚描述目标

不好的写法：

```md
更多内容参见[这里](/web-documentation/ui/table)。
```

好的写法：

```md
参见[如何呈现表格](/web-documentation/ui/table)。
```

清晰的描述性文字能帮助读者（以及屏幕阅读器等无障碍工具）理解链接指向何处，而无需阅读周围的上下文。

---

## 13. 图片

图片使用与链接类似的语法，前面加上一个 `!`。

**代码**

```md
![系统架构图](/images/architecture.png)
```

`[]` 中的文字是 **alt 文本**，用于向屏幕阅读器描述图片内容，并在图片加载失败时显示。

:::caution[警告]
不要将 alt 文本留空（`![]()`）或写得过于笼统，如 `![image]()`。alt 文本应准确描述图片内容，这对无障碍访问（accessibility）尤为重要。
:::

## 14. 段落内换行

Markdown 默认会**忽略**同一段落内的单个换行符。

**代码**

```md
第一行。
第二行。
```

**效果**

第一行。
第二行。

以上两行在渲染时仍会合并为一段。要强制换行，可以在行末添加两个空格，或使用 `<br />` 标签。

**代码**

```md
第一行。<br />
第二行。
```

**效果**

第一行。<br />
第二行。

:::tip
在技术文档中，应优先拆分成独立段落或使用列表，而不是强行换行，因为依赖行末空格的换行方式在文件重新格式化时很容易丢失。
:::

## 15. 转义特殊字符

某些字符在 Markdown 中具有特殊含义（`*`、`_`、`` ` ``、`#`、`|`、`[`、`]`……）。要将它们作为普通文本显示，需要用 `\` 进行转义。

**代码**

```md showLineNumbers title="转义字符"
在 Markdown 中使用 \*bold\* 来表示粗体。
```

**效果**

在 Markdown 中使用 \*bold\* 来表示粗体。

参见[表格中包含 `|`](/web-documentation/ui/table#20-table-có-dấu--bên-trong-nội-dung)，了解当 `|` 出现在表格中时应如何转义。

## 16. 组合多种格式

以上格式可以在同一段落中组合使用。

**代码**

```md showLineNumbers title="组合格式"
**`apiKey`** 参数是*必填*的。如果缺失，请求将返回 `401` 错误。参见[身份验证](/web-documentation/authentication)。
```

**效果**

**`apiKey`** 参数是*必填*的。如果缺失，请求将返回 `401` 错误。参见[身份验证](/web-documentation/ui/typography)。

:::caution[警告]
在同一句话中组合过多格式（粗体、斜体、代码、链接同时使用）会让句子难以阅读。只强调真正必要的部分。
:::

## 17. 什么时候该用哪种格式？

选错格式会让读者误判信息的重要程度或类型。

一个简单的规则：

| 用途                                  | 格式         |
| -------------------------------------- | ------------ |
| 变量、函数、文件、命令、技术性数值    | 行内代码     |
| 强调重要的词语/短语                   | **粗体**     |
| 术语、专有名词、轻微强调              | *斜体*       |
| 已过时、不再适用的内容                | ~~删除线~~   |
| 轻量引用或补充说明                    | 引用         |
| 需要突出的警告或提示                  | 提示框       |
| 按顺序执行的步骤                      | 有序列表     |
| 顺序不重要的列表                      | 无序列表     |
| 行/列数据                             | 表格         |

:::tip
如果不确定该用粗体还是行内代码，可以问自己：“这是一个具体的技术概念（变量名、命令……），还是句子中只是需要强调的一个普通词语？”技术概念 → 行内代码。普通强调 → 粗体。
:::

## 18. 不要滥用格式

一个段落使用过多不同的格式会失去清晰度。

不推荐：

```md
***注意***：`id` 参数必须是***`string`***类型，~~不能为空~~，并且**`不能`**与已存在的 id 重复。
```

推荐：

```md
`id` 参数必须是 `string` 类型，且不能与已存在的 `id` 重复。

:::caution
`id` 不能为空。
:::
```

将警告从主句中分离出来，用提示框单独呈现，而不是试图在同一句话中强调所有内容。

## 20. 撰写排版内容前的检查清单

在完善一个文档页面之前，问自己以下问题：

* 标题是否从 `##` 开始，且层级顺序正确？
* 段落是否足够简短，每段是否聚焦于一个要点？
* 粗体是否被滥用？
* 变量名、函数名、文件名、命令是否都使用了行内代码？
* 过时的内容是否使用了删除线，而不是直接删除（如果仍需保留引用）？
* 链接文字是否清楚描述了目标，而不是使用“这里”？
* 图片是否有准确描述内容的 alt 文本？
* 特殊字符（`|`、`*`、`_`……）是否在需要的地方进行了转义？
* 是否有段落应该改成列表或表格，而不是用长篇文字表达？
* 是否有段落应该使用提示框，而不是靠粗体/斜体强行强调？

---

## 总结

排版是每个文档页面的基础层。在考虑表格、提示框或 Mermaid 等更复杂的组件之前，必须先确保标题、段落和基本格式的使用是正确的。

最重要的原则：

1. **正文中的标题从 `##` 开始**，不要使用 `#`，因为页面 title 已经充当一级标题。
2. **标题必须按正确的层级顺序**，不能跳级。
3. **段落应简洁**，每段聚焦一个要点。
4. **凡是技术性内容都使用行内代码**：变量、函数、文件、命令、值。
5. **粗体用于有选择性的强调**，不要到处使用。
6. **轻量内容用引用，需要突出的警告用提示框。**
7. **链接需要清晰的描述性文字**，不要用“这里”。
8. **图片需要准确描述内容的 alt 文本。**
9. **特殊字符需要在适当的地方进行转义。**
10. **结构化数据优先使用列表和表格**，而不是冗长的文字叙述。

一个排版良好的文档页面，并不是使用格式最多的页面，而是能让读者**最快找到所需信息**的页面。
