## 1. Overall view

The SDK is an **iOS library (XCFramework `ISdk`)** that packages 3 main responsibilities:

1. **Realtime connection** to the Interactive server via Socket.IO (Live scenario).
2. **Orchestrating the display** of interactive content (written in web) inside transparent `WKWebView`s.
3. **Forwarding user actions** to the server via REST and **calling back** into the app through delegates.

## 2. Layers and responsibilities

| Layer | Component (file) | Responsibility |
|---|---|---|
| **Facade / Orchestrator** | `InteractiveControllerView` | The app's single entry point. Receives commands (`joinRoom`, `initAuthenToken`, `getTimeVideo`, `releaseAll`…), listens to socket events, decides the overlay type (minigame / predict / lucky), coordinates the managers |
| **Configuration** | `InteractiveSetting` | Writes the environment (`KEY_ENABLE_PROD_ENV`) and tenant (`KEY_X_TENANT_ID`) into `UserDefaults` |
| **Realtime transport** | `SocketIOManagementImpl` (`SocketIOManagement`) | Creates/tears down the socket, registers events, normalizes payloads, sends emit-ack |
| **Overlay orchestration** | `OverlayManagementImpl` (`OverlayManagement`) | Builds the minigame overlay, handles the answer flow (login → fanclub → VIP/bet → call API), tracking |
| **Predict/lucky orchestration** | `PredictManagementImpl` | The floating GIF button, the predict/lucky-number dialog, its own answer flow |
| **WebView presentation** | `UIOverlay`, `ConfigureWebView` (`NoZoomWKWebView`) | Creates the transparent `WKWebView`, attaches/removes it per the overlay lifecycle |
| **Auxiliary presentation** | `DialogLuckyNumberView`, `DialogPredictView`, `DialogConfirmView`, `DialogDeductionView`, `FanClubView`, `LeaderboardView` | Full-screen dialogs / floating button / leaderboard |
| **Bridge** | `OverlayWebViewCallBack`, `PredictWebViewCallBack` | JavaScript ⇄ Swift bridge (`WKScriptMessageHandler`, interface name `IOS`) |
| **REST** | `LiveLogRepository` (`/api/actions`), `TelcoRepository` (`/api/public/vip-status`), `LiveCompensatoryShotImpl` (`interactive-status`), the `OverlayVod*` classes (VOD) | Calls the API via Alamofire |
| **Observability** | `OverlayTracking.swift` (`OverlayTrackingSession`, `OverlayTrackingFactory`) | Measures the overlay lifecycle and sends `emit-ack` |
| **Infrastructure** | `ApiConst`, `TypeInteractive`, `SocketEvents`, `Utils`, `PrintLog`, the `Codable` models | Constants, utilities, data models |

### Design principles reflected in the code

- **A single facade for the app**: the app mainly touches `InteractiveControllerView` + `InteractiveSetting` +
  the delegate `protocol`s. The sub-managers are still `public` but usually don't need to be called directly.
- **Events flow through a single callback**: the socket pushes into the SDK via a `(String, Any) -> ()` closure
  attached through `addCallback` (single-slot); `InteractiveControllerView.handleEventsSocket()` `switch`es on
  the event name.
- **Interactive content is web-based**: the SDK doesn't draw the question UI itself — it just loads a
  template URL into a `WKWebView` and exchanges data via `postMessage`. Changing the interactive UI doesn't
  require rebuilding the app.
- **Configuration lives in `UserDefaults`**: the environment and tenant are read back everywhere (socket
  headers, choosing the REST base URL…). This is also the source of some **force-unwrap crashes** when not
  configured.

## 4. Two operating modes

### 4.1. LIVE (`type = 1`, `ApiConst.TYPE_LIVE`) — server-driven

The server actively pushes overlays via Socket.IO. Display/answer conditions (login, fanclub, VIP/bet,
already answered or not) are checked directly on the client.

```mermaid
graph LR
    S["Socket.IO"] -->|"overlay / ex-overlay"| SIO["SocketIOManagementImpl"]
    SIO -->|"callback OVERLAY"| ICV["InteractiveControllerView"]
    ICV -->|"typeTimeline"| R{"Routing"}
    R -->|"3 / 5"| P["PredictManagementImpl<br/>(button + dialog)"]
    R -->|"other"| M["OverlayManagementImpl.showOverlayLive<br/>(minigame WebView)"]
```

### 4.2. VOD (`type = 2`, `ApiConst.TYPE_VOD`) — driven by playback progress

There is no socket. The SDK preloads the entire scenario via REST, and then **the app must feed the
playback time**:

```mermaid
graph LR
    OM["joinRoom(type=2)"] --> API["GET /api/ctc/scenario/v2/vod/{mediaId}/{os}"]
    API --> CONV["convertVodInteractive()<br/>filters timelines with showStatus == ACTIVE,<br/>sorted by timeShow (seconds)"]
    CONV --> LIST["listTimelinesVod (in memory)"]
    APP["App: interactive.getTimeVideo(time: seconds)"] --> CHK["matches timeShow == Int(time)"]
    LIST --> CHK
    CHK -->|"matched on the exact second"| SHOW["showOverlayVod()"]
    CHK --> RM["removes the shown timeline from the list"]
```

> `timeShow` is derived from `Timelines.time` (format `"SS"`, `"MM:SS"`, or `"HH:MM:SS"`, via the
> `parseTimeToSeconds` function), so the unit fed into `getTimeVideo` is **seconds**.

## 5. Threading model

| Task | Thread | Note |
|---|---|---|
| Socket.IO events | Socket.IO client's thread | Forwarded into the `addCallback` closure |
| Building/destroying the WebView | **Main thread** | `showInteractive`/`setUpDataForTemplatePredict` are called inside `DispatchQueue.main.async` |
| REST calls | Alamofire's thread, callback returns to main | `AF.request(...).response*` |
| Tracking emit-ack | Synchronous inside `OverlayTrackingSession` (flags `emittedStages`, `finished`) | The render timer uses `Timer` on main |
| Predict button image/alpha change | Main (`Timer.scheduledTimer`) | Fades alpha to 0.5 after **5 seconds** |

> Unlike the Android version, iOS has **no** `QueuedMutableLiveData` — overlay events are processed
> sequentially right inside the callback. `addCallback` is a **single slot**; a later call overwrites
> the previous one.

## 6. Object lifecycle

```mermaid
stateDiagram-v2
    [*] --> Configured: InteractiveSetting.setEnableProdEnv + setXTenantId
    Configured --> Created: InteractiveControllerView()
    Created --> Ready: initOverlay(uiView, predictView) + initAuthenToken(...)

    Ready --> Live: joinRoom(mediaId, 1)
    Ready --> Vod: joinRoom(mediaId, 2)

    Live --> Live: receives overlay / predict / lucky
    Live --> Ready: leaveRoom() / releaseAll() / new joinRoom()
    Vod --> Vod: getTimeVideo(t)
    Vod --> Ready: releaseAll() / new joinRoom()

    Ready --> [*]: releaseAll()
```

Important points in the code:

- **The `InteractiveControllerView()` constructor only creates `SocketIOManagementImpl` and
  `OverlayManagementImpl`** — no connection is opened yet, no API is called yet.
- **`joinRoom(type: 1)`** leaves the previous room (if a different media), disconnects the old socket,
  calls `removeAllView()`, re-attaches the socket callback, then `connectSocket()`. `emit("join-room")`
  only happens **after the socket connects successfully** (in the `SocketEvents.CONNECTED` branch).
- **`joinRoom(type: 2)`** disconnects the socket (if open), calls `removeAllView()`, calls the REST API
  to load the VOD scenario.
- **Calling `initAuthenToken()` while connected with an active media** → disconnects the socket and calls
  `joinRoom(type: 1)` again so the socket carries the new token.
- **`releaseAll()`** calls `leaveRoom()` (if connected), removes all delegates, and calls
  `disconnection()`.

    OMI->>OMI: setupAlignment() → location 0..8, calls locationLayoutViewRoot()

## 8. WebView bridge protocol

The SDK attaches a `WKScriptMessageHandler` named **`IOS`** (`userContentController.add(callBack, name: "IOS")`).

**Web → SDK** (`window.webkit.messageHandlers.IOS.postMessage(jsonString)`) — decoded into
`OverlayDataCallback { data, type }`:

| `type` (`TypeInteractive` constant) | Meaning |
|---|---|
| `INTERACTIVE_SHOW_ANALYTICS` | Overlay has been shown → `showLayoutViewRoot()`, hides player controls |
| `INTERACTIVE_HIDE_ANALYTICS` | Overlay closed → removes the WebView, cleans up tracking, shows player controls again |
| `INTERACTIVE_ACTION_REPORT` | User answers / taps an ad (`action = CLICK_ADS`) |
| `INTERACTIVE_OPEN_ANALYTICS` / `INTERACTIVE_CLOSE_ANALYTICS` | Opens/closes the predict/lucky dialog (handled in `PredictManagementImpl`) |
| `INTERACTIVE_PING_ANALYTICS` | Only used for filtering, not logged |

**SDK → Web** (`webView.evaluateJavaScript("window.postMessage('<json>', '*')")`):

| `key` | When | Emitted from |
|---|---|---|
| `UPDATE_DATA_INTERACTIVE` | Socket `update-result` | `sendMessageResultinteractive()` |
| `UPDATE_COUTER` *(kept as-is, missing the "N")* | Socket `predict-result` → `answer1/answer2` | `receiveDataResultPredict()` + when reopening the dialog |
| `UPDATE_NUMBER_LUCKY` | API returns the lucky result | `postMessageWhenClickPlayLucky()` |
| `UPDATE_CONFIRM` | Answer submitted successfully (bet/VIP branch) | `postMessageWhenAnswerSuccess()` |

> ⚠️ Unlike the Android version, iOS does **not** use the `LOADED_OVERLAY` / `GET_DATA_INTERACTIVE` keys.
> The iOS template is loaded directly with a URL that already carries all parameters; additional data
> (results) is only pushed down afterward via the keys above.

## 9. Environment & tenant configuration

```mermaid
graph LR
    SET["InteractiveSetting"] -->|"setEnableProdEnv(dev/stg/prod)"| K1["UserDefaults KEY_ENABLE_PROD_ENV"]
    SET -->|"setXTenantId(...)"| K2["UserDefaults KEY_X_TENANT_ID"]
    K1 --> WSK["Chooses the base WSK URL + base REST URL"]
    K2 --> H1["Socket header: x-tenant-id"]
    K2 --> H2["REST header: X-TENANT-ID"]
    K2 --> RULE["Tenant-specific rules (login / fanclub / predict button)"]
```

- `Enviroment` = `DEV` (`"dev"`) / `STG` (`"stg"`) / `PROD` (`"prod"`) — selects both the socket URL
  (`*.onplay.live` WSK) and the REST URL and the leaderboard URL.
- `TenantIdType`: `vtvlive` (OnPlus), `onlivev2` = `onliveLiveStream` (SOOP), `onlivetv` = `onliveTV`
  (OnLive TV), `VTVprime` (SeeNow). Some tenant-specific rules in the current code:
  - **The predict/lucky button is skipped** for tenants `vtvlive`, `onlivetv`, `VTVprime`
    (`receiveDataActionButtonPredict` returns early).
  - **Only tenant `onlivev2`** applies the `&fanclub=false` parameter when the user is not yet a
    fanclub member.
- `ApiConst.OS = "iphone"` goes into the socket `os` header, the `os` field of the `/api/actions` body,
  the `os` parameter of the VOD scenario URL, and the overlay `targets` filtering condition
  (`targets.contains("iphone")` or `"all"`).

## 10. Local storage (`UserDefaults`)

| Key / suite | Purpose |
|---|---|
| `KEY_ENABLE_PROD_ENV`, `KEY_X_TENANT_ID` | Environment + tenant (must be configured beforehand) |
| `KEY_MEDIA_CONTENT_ID` | The most recently joined media |
| `MINI_GAMES`, `PREDICT`, `POPUP_PREDICT`, `INTERACTIVE_TYPE_TIMELINE` | Display state machine (`SHOW`/`HIDE`/`HIDE_CMS`/`END`) |
| `KEY_FAN_CLUB` | Whether the user belongs to the fanclub of the currently viewed media |
| suite `INTERACTIVE_<userId>` / `INTERACTIVE_DEFAULT`, key = `mediaId` | `Compensatory` — prevents redisplaying/re-answering a given timepoint |
| suite `DATA_RESULT_PREDICT`, key = `timelineId` | Caches the predict result (`answer1`/`answer2`) to push again when the dialog is reopened |
