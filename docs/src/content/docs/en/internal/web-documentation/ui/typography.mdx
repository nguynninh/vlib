title: "Typography"
description: "How to use typography (headings, paragraphs, bold, italic, lists, blockquotes, links, inline code...) in MDX, along with rules for presenting text in technical documentation."
---

Typography is the foundation of every documentation page. Before thinking about Tables, Callouts, or Code Blocks, most of the content is still headings, paragraphs, and basic text formatting.

A page with correct content but messy typography — wrong heading levels, bold used everywhere, paragraphs that go on forever — still makes it hard for readers to absorb information.

For example, instead of writing one long, unstructured block of text:

```md title="No structure"
To install the package you need to run npm install, then create a config.json file, and it's important to fill in the correct API key or the app won't start.
```

it's better to split it into clear headings, paragraphs, and inline code.

---

## 1. Headings

Headings structure content into levels. In Markdown, a heading is created with `#`, and the number of `#` characters corresponds to the heading level.

**Code**

```md showLineNumbers title="Heading levels"
# Heading 1
## Heading 2
### Heading 3
#### Heading 4
```

In Starlight, the page's `title` (declared in frontmatter) already acts as Heading 1. So content on the page should start from `##` (Heading 2) downward.

```mdx title="Frontmatter"
---
title: "Page name"
---
```

:::caution[Warning]
Don't use `#` (Heading 1) in Starlight MDX content, since the page already has its own title acting as Heading 1. Adding another `#` in the content creates two level-1 headings on the same page, confusing the outline structure and SEO.
:::

### Heading order

Headings should follow their hierarchy in order — don't skip levels.

Not recommended:

```md title="Skipping heading levels"
## Section
#### Sub-section
```

when jumping directly from `##` to `####` while skipping `###`.

Recommended:

```md title="Correct heading order"
## Section
### Sub-section
```

### Keep headings short

Good:

```md
## User Authentication
```

Not good:

```md
## How user authentication works in this system and why it matters
```

Long headings weaken the table of contents, making it harder for readers to scan quickly.

## 2. Paragraphs

A paragraph is a normal block of text, separated by a blank line.

**Code**

```md showLineNumbers title="Paragraphs"
This is the first paragraph.

This is the second paragraph.
```

**Result**

This is the first paragraph.

This is the second paragraph.

:::caution[Warning]
Without a blank line between two paragraphs, Markdown will merge them into a single paragraph instead of keeping them as two separate lines.
:::

### Keep paragraphs short

In technical documentation, a paragraph should focus on a single idea, usually no more than 3-4 sentences.

Avoid writing one long paragraph that lists many different ideas. If the content has multiple points, use a list or table instead of cramming everything into one paragraph.

---

## 3. Bold

Bold emphasizes an important word or phrase, created with two `**` characters.

**Code**

```md showLineNumbers title="Bold"
The `timeout` parameter is **required** when calling this API.
```

**Result**

The `timeout` parameter is **required** when calling this API.

:::caution[Warning]
Don't overuse bold on too many words in the same paragraph. If everything is bold, nothing stands out, and bold loses its emphasis.
:::

---

## 4. Italic

Italic is created with a single `*` or `_`, commonly used for terminology, proper nouns, or light emphasis.

**Code**

```md showLineNumbers title="Italic"
In Git, this operation is called *rebase*.
```

**Result**

In Git, this operation is called *rebase*.

Bold and italic can be combined with three `***` characters.

**Code**

```md
This warning is ***very important***.
```

**Result**

This warning is ***very important***.

---

## 5. Strikethrough

Strikethrough is created with two `~~` characters, used to mark content that's outdated or no longer applicable.

**Code**

```md showLineNumbers title="Strikethrough"
~~`getUserById`~~ is deprecated, use `findUserById` instead.
```

**Result**

~~`getUserById`~~ is deprecated, use `findUserById` instead.

---

## 6. Inline code

Inline code is created with backticks `` ` ``, used for variable names, functions, files, commands, or technical values appearing within a sentence.

**Code**

```md showLineNumbers title="Inline code"
Run `npm run build` to generate files in the `dist/` folder.
```

**Result**

Run `npm run build` to generate files in the `dist/` folder.

Use inline code for:

* Variable, function, and class names.
* File and folder names.
* Terminal commands.
* Specific values (`true`, `null`, `200`).
* Environment variable names.

:::tip
If a piece of inline code needs to contain a backtick itself, wrap it with double backticks: `` `code` ``.
:::

---

## 7. Unordered lists

An unordered list is created with `-`, `*`, or `+` at the start of a line.

**Code**

```md showLineNumbers title="Unordered list"
* Install dependencies.
* Configure the environment.
* Run migrations.
```

**Result**

* Install dependencies.
* Configure the environment.
* Run migrations.

:::tip
Pick a single marker (`-`, `*`, or `+`) and use it consistently throughout a document, so the source is easier to read.
:::

### Nested lists

**Code**

```md showLineNumbers title="Nested list"
* Frontend
    * React
    * Vue
* Backend
    * Node.js
    * Spring Boot
```

**Result**

* Frontend
    * React
    * Vue
* Backend
    * Node.js
    * Spring Boot

Nested items should be indented with 4 spaces (or one tab) per level, to avoid the parser misreading the nesting.

---

## 8. Ordered lists

An ordered list uses numbers followed by a `.`.

**Code**

```md showLineNumbers title="Ordered list"
1. Clone the repository.
2. Install dependencies.
3. Run the application.
```

**Result**

1. Clone the repository.
2. Install dependencies.
3. Run the application.

:::note
Markdown automatically renumbers items when rendering, so even if you write `1. 1. 1.` in the source, the rendered result is still `1. 2. 3.`. Still, write the correct numbers in the source for readability.
:::

### When to use an ordered list instead of unordered?

| Situation                                | List type |
| ----------------------------------------- | :-------: |
| Steps that must be performed in order    | Ordered   |
| A list where order doesn't matter        | Unordered |

If changing the order of items changes the outcome (e.g., installation steps), use an ordered list.

## 9. Task lists

Some Markdown flavors (including the GitHub-Flavored Markdown Starlight supports) allow checkboxes in lists.

**Code**

```md showLineNumbers title="Task list"
- [x] Write the API endpoint.
- [x] Write unit tests.
- [ ] Write documentation.
```

**Result**

- [x] Write the API endpoint.
- [x] Write unit tests.
- [ ] Write documentation.

Task lists are suited for progress checklists, and shouldn't replace a more complex status table.

## 10. Blockquotes

A blockquote is created with `>` at the start of a line, used for quoting or lightly emphasizing a sentence — a lower level than a Callout.

**Code**

```md showLineNumbers title="Blockquote"
> `timeout` defines the maximum time a client waits for a response before the request is considered failed.
```

**Result**

> `timeout` defines the maximum time a client waits for a response before the request is considered failed.

### How is a blockquote different from a Callout?

| Component  | Purpose                                                  |
| ---------- | ---------------------------------------------------------- |
| Blockquote | Quoting, light supplementary explanation, no strong emphasis needed |
| Callout    | Warnings or notes that need to grab the reader's attention |

See [Callouts](/internal/web-documentation/ui/callout) to learn when to use `note`, `tip`, `caution`, or `danger` instead of a blockquote.

Blockquotes can be nested using multiple `>` characters.

**Code**

```md
> The original quote.
>
> > A comment on the quote.
```

**Result**

> The original quote.
>
> > A comment on the quote.

---

## 11. Horizontal rules

A horizontal rule is created with three `-`, `*`, or `_` characters on their own line, used to separate major sections of content.

**Code**

```md
---
```

This document uses horizontal rules to separate major sections (`## 1.`, `## 2.`...), helping readers spot the boundaries between them.

:::caution[Warning]
If you place `---` right at the start of a file with no preceding content, some Markdown parsers (including Astro/Starlight frontmatter) may misinterpret it as the frontmatter boundary. Only use `---` as a horizontal rule in the middle of the content, after the frontmatter.
:::

## 12. Links

Links use the syntax `[text](url)`.

**Code**

```md showLineNumbers title="Link"
See [Tables](/internal/web-documentation/ui/table) to learn how to present tabular data.
```

**Result**

See [Tables](/internal/web-documentation/ui/table) to learn how to present tabular data.

### Internal vs. external links

| Link type | Example                                  |
| --------- | ----------------------------------------- |
| Internal  | `[Table](/internal/web-documentation/ui/table)`    |
| External  | `[Astro](https://astro.build/)`           |

:::tip
For internal links, use a site-relative path (`/internal/web-documentation/...`) instead of hardcoding the full domain, so the link still works if the domain changes or on a staging environment.
:::

### Link text should be descriptive

Not good:

```md
See more [here](/internal/web-documentation/ui/table).
```

Good:

```md
See [how to present Tables](/internal/web-documentation/ui/table).
```

Descriptive text helps readers (and accessibility tools like screen readers) understand where a link goes without needing to read the surrounding context.

---

## 13. Images

Images use syntax similar to links, with a `!` prefix.

**Code**

```md
![System architecture diagram](/images/architecture.png)
```

The text in `[]` is the **alt text**, describing the image content for screen readers and displaying when the image fails to load.

:::caution[Warning]
Don't leave alt text empty (`![]()`) or generic like `![image]()`. Alt text should accurately describe the image content — this matters a lot for accessibility.
:::

---

## 14. Line breaks within a paragraph

By default, Markdown **ignores** a single line break within the same paragraph.

**Code**

```md
First line.
Second line.
```

**Result**

First line.
Second line.

The two lines above still render joined into one paragraph. To force a line break, add two trailing spaces at the end of the line, or use the `<br />` tag.

**Code**

```md
First line.<br />
Second line.
```

**Result**

First line.<br />
Second line.

:::tip
In technical documentation, prefer splitting into separate paragraphs or using a list instead of forcing line breaks, since trailing-space line breaks are easily lost when a file gets reformatted.
:::

## 15. Escaping special characters

Some characters have special meaning in Markdown (`*`, `_`, `` ` ``, `#`, `|`, `[`, `]`...). To display them as plain text, escape them with a `\`.

**Code**

```md showLineNumbers title="Escaping characters"
Use \*bold\* to bold text in Markdown.
```

**Result**

Use \*bold\* to bold text in Markdown.

See [Tables containing `|`](/internal/web-documentation/ui/table#20-table-có-dấu--bên-trong-nội-dung) for how to escape `|` when it appears inside a table.

## 16. Combining multiple formats

The formats above can be combined within the same paragraph.

**Code**

```md showLineNumbers title="Combining formats"
The **`apiKey`** parameter is *required*. If missing, the request returns a `401` error. See [Authentication](/internal/web-documentation/authentication).
```

**Result**

The **`apiKey`** parameter is *required*. If missing, the request returns a `401` error. See [Authentication](/internal/web-documentation/ui/typography).

:::caution[Warning]
Combining too many formats in the same sentence (bold, italic, code, and links all at once) makes it hard to read. Only emphasize what's genuinely necessary.
:::

---

## 17. Which format should you use, and when?

Choosing the wrong format leads readers to misjudge the importance or type of information.

A simple rule of thumb:

| Purpose                                        | Format          |
| ------------------------------------------------ | ---------------- |
| Variable, function, file, command, technical value | Inline code     |
| Emphasizing an important word/phrase             | **Bold**        |
| Terminology, proper nouns, light emphasis        | *Italic*        |
| Outdated content, no longer applicable           | ~~Strikethrough~~ |
| Light quote or supplementary explanation         | Blockquote      |
| Warnings or notes that need to stand out         | Callout         |
| Steps that follow an order                       | Ordered list    |
| A list where order doesn't matter                | Unordered list  |
| Row/column data                                  | Table           |

:::tip
If you're unsure whether to use bold or inline code, ask yourself: "Is this a specific technical concept (variable name, command...) or just a word that needs emphasis in the sentence?" Technical concept → inline code. Regular emphasis → bold.
:::

---

## 18. Don't overuse formatting

A paragraph that uses too many different formats loses its clarity.

Not recommended:

```md
***Note***: the `id` parameter must be a ***`string`***, ~~cannot be empty~~ and **`must not`** duplicate an existing id.
```

Recommended:

```md
The `id` parameter must be a `string` and must not duplicate an existing `id`.

:::caution
`id` cannot be empty.
:::
```

when the warning is separated from the main sentence using a Callout, instead of trying to emphasize everything in a single sentence.

## 19. Typical documentation page structure

Combining the typography components above, a typical technical documentation page usually follows this structure:

```md title="Documentation page structure"
---
title: "Page name"
description: "A short description"
---

A brief introduction to the page's content.

---

## 1. First section

An explanatory paragraph.

**Code**

​```ts
// example code
​```

**Result**

The corresponding output.

---

## Summary

A concise wrap-up and the key principles.
```

This structure stays consistent with other pages in the Web Documentation section, such as [Callouts](/internal/web-documentation/ui/callout) and [Tables](/internal/web-documentation/ui/table).

## 20. Checklist before writing Typography

Before finalizing a documentation page, ask yourself:

* Do headings start from `##` and follow the correct hierarchy?
* Are paragraphs short enough, with each one focused on a single idea?
* Is bold being overused?
* Have variable, function, file, and command names been marked as inline code?
* Has outdated content been struck through instead of deleted outright (if the reference still needs to be kept)?
* Does link text describe its destination clearly, instead of using "here"?
* Do images have alt text that accurately describes their content?
* Have special characters (`|`, `*`, `_`...) been escaped where needed?
* Is there any paragraph that should become a list or table instead of prose?
* Is there any paragraph that should use a Callout instead of forcing emphasis with bold/italic?

---

## Summary

Typography is the foundation layer of every documentation page. Before considering more complex components like Tables, Callouts, or Mermaid, headings, paragraphs, and basic formatting need to be used correctly.

The most important principles:

1. **Headings in the content start from `##`**, never `#`, since the page title already serves as Heading 1.
2. **Headings must follow the correct hierarchy**, without skipping levels.
3. **Paragraphs should be concise**, each focused on a single idea.
4. **Use inline code for anything technical**: variables, functions, files, commands, values.
5. **Use bold for selective emphasis**, not everywhere.
6. **Use blockquotes for light content, Callouts for warnings that need to stand out.**
7. **Links need descriptive text**, not "here".
8. **Images need alt text that accurately describes their content.**
9. **Special characters need to be escaped where necessary.**
10. **Prefer lists and tables for structured data**, instead of lengthy prose.

A documentation page with good typography isn't one that uses the most formatting — it's one that helps readers **find the information they need the fastest**.
