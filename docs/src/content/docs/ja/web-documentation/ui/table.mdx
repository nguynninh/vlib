Table は技術ドキュメントを書くうえで最も重要な要素の1つです。

同じ構造を持つ情報を長い文章で説明する代わりに、table を使ってそれらを並べて配置すれば、読者はすばやく比較できます。

例えば、次のように書く代わりに:

:::note
TypeScript はフロントエンドで使われます。Java は Android で使われます。Swift は iOS で使われます。
:::

次のように書くことができます。

| Platform | Language   |
| -------- | ---------- |
| Web      | TypeScript |
| Android  | Kotlin     |
| iOS      | Swift      |

この方法は、ドキュメントで次のような内容を表現する必要がある場合に特に役立ちます。

* 複数の選択肢の比較。
* 属性の一覧。
* API parameters。
* Configuration options。
* Environment variables。
* HTTP status codes。
* Supported platforms。
* Feature comparison。
* Version compatibility。
* Database fields。
* CLI commands。
* Keyboard shortcuts。

## 1. 基本的な Table 構文

最小限の Markdown Table は次の要素で構成されます。

1. Header row。
2. Separator row。
3. 1つ以上の data row。

**コード**

```mdx showLineNumbers title="基本的な Table"
| Name | Type | Description |
| --- | --- | --- |
| `id` | `string` | Unique identifier |
| `name` | `string` | User name |
| `email` | `string` | User email |
```

**デモ**

| Name    | Type     | Description       |
| ------- | -------- | ----------------- |
| `id`    | `string` | Unique identifier |
| `name`  | `string` | User name         |
| `email` | `string` | User email        |

次の行:

```md
| --- | --- | --- |
```

は header と本文を区切るために使われます。

`---` の数は、区切り部分として有効である限り重要ではありません。

例えば:

```md
| Name | Type |
| - | - |
| id | string |
```

でも table として render されます。

ただし、ソースコードを読みやすくするために `---` を使うことをおすすめします。

## 2. Table の Header

Header は table の最初の行で、各 column の意味を説明するために使われます。

例:

**コード**

```mdx showLineNumbers title="Header を持つ Table"
| Property | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | `string` | Yes | User identifier |
| `name` | `string` | Yes | User name |
| `avatar` | `string` | No | Avatar URL |
```

**デモ**

| Property | Type     | Required | Description     |
| -------- | -------- | -------- | --------------- |
| `id`     | `string` | Yes      | User identifier |
| `name`   | `string` | Yes      | User name       |
| `avatar` | `string` | No       | Avatar URL      |

Header は簡潔で分かりやすいものにすべきです。

避けるべき例:

| This is the property name of the object | This is the data type of the property | Is this property required? |
| --------------------------------------- | ------------------------------------- | --------------------------- |

推奨される例:

| Property | Type | Required |
| -------- | ---- | -------- |

Header が短いほど、table は素早く読み取りやすくなります。

## 3. Column の数

各 row は同じ数の column を持つべきです。

**コード**

```mdx showLineNumbers title="Column の数"
| Name | Type | Description |
| --- | --- | --- |
| `id` | `string` | Identifier |
| `name` | `string` | User name |
| `email` | `string` | Email |
```

**デモ**

| Name    | Type     | Description |
| ------- | -------- | ----------- |
| `id`    | `string` | Identifier  |
| `name`  | `string` | User name   |
| `email` | `string` | Email       |

column の数が一致しない table を作るべきではありません。

```md
| Name | Type | Description |
| --- | --- | --- |
| id | string |
| name | string | User name | Extra |
```

一部の Markdown renderer はこの構造を自動的に修正しようとしますが、パーサーによって結果が異なることがあります。

そのため、各 row が正しい数の column を持つようにしてください。

:::caution[警告]
header に対して column が不足していたり多すぎたりするのは、table を手動でコピー&ペーストしたり編集したりする際に非常に起こりやすいミスです。commit する前に、各 row の `|` の数を確認してください。
:::

## 4. 単一 Column の Table

Markdown Table は1つの column でも使用できます。

**コード**

```mdx showLineNumbers title="単一 Column"
| Supported Format |
| --- |
| Markdown |
| MDX |
| HTML |
```

**デモ**

| Supported Format |
| ---------------- |
| Markdown         |
| MDX              |
| HTML             |

ただし、単純なリストであれば、Markdown list の方が適していることが多いです。

```md
- Markdown
- MDX
- HTML
```

単一 column の table は、データが本当に表形式の意味を持つ場合にのみ使うべきです。

## 6. Column の配置(Alignment)

Markdown Table は `:` を使って左揃え、右揃え、中央揃えをサポートしています。

### 左揃え

```md
| Name | Type |
| :--- | :--- |
| id | string |
```

### 中央揃え

```md
| Name | Type |
| :---: | :---: |
| id | string |
```

### 右揃え

```md
| Name | Type |
| ---: | ---: |
| Price | 100 |
```

3つを組み合わせることもできます。

**コード**

```mdx showLineNumbers title="Column Alignment"
| Property | Type | Required | Default |
| :--- | :---: | :---: | ---: |
| `id` | `string` | Yes | - |
| `limit` | `number` | No | 20 |
| `enabled` | `boolean` | No | true |
```

**デモ**

| Property  |    Type   | Required | Default |
| :-------- | :-------: | :------: | ------: |
| `id`      |  `string` |    Yes   |       - |
| `limit`   |  `number` |    No    |      20 |
| `enabled` | `boolean` |    No    |    true |

### Column の幅

標準の Markdown Table には、`:---` や `---:` を含め、column の**固定幅を指定する構文がありません**。これらは alignment を制御するだけで、width は制御しません。

```md
| Name | Description |
| --- | --- |
| id | Unique identifier |
```

ブラウザに実際に表示される幅は、区切り行に書いた `-` の数ではなく、その column の中で最も長い内容に基づいて自動的に計算されます。

:::caution[警告]
ある column の `-` を増やせば(例えば `----------`)render 時に広くなると考えるのはよくある誤解です。それはソースコードを読みやすくするだけで、実際の表示結果には影響しません。
:::

このドキュメントでは、width を実際に制御する必要がある場合(例えばある column が狭すぎたり広すぎたりするのを避けたい場合)、その column の header に `[width=...]` または `[w=...]` を追加します。

:::danger[よくあるエラー]
角括弧の構文 `[width=...]` または `[w=...]` のみを使ってください。`{width=...}`、`<width=...>` などの他の書き方は使わないでください。MDX は `{...}` を JSX expression として解釈し、ページのビルドエラーを引き起こす可能性があります。
:::

最初の column を `200px` の固定幅にし、残りの column はブラウザに自動計算させる例:

```mdx showLineNumbers title="Markdown Table で width を強制する"
| Name [width=200px] | Description |
| --- | --- |
| `id` | Unique identifier |
```

**デモ**

| Name [width=200px] | Description |
| --- | --- |
| `id` | Unique identifier |

`[width=...]` の部分はレイアウトの render にのみ使われ、header には表示されません。この方法は使いすぎるべきではありません。固定幅を多用しすぎると、モバイルで table が読みにくくなることがあります。

## 7. 左揃え、中央揃え、右揃えはいつ使うべきか

配置をランダムに決めるべきではありません。

シンプルなルールとして:

| 内容        | Alignment |
| ----------- | --------- |
| Text        | Left      |
| Description | Left      |
| コード        | Left      |
| Status      | Center    |
| Boolean     | Center    |
| Number      | Right     |
| Price       | Right     |
| Percentage  | Right     |

例:

**コード**

```mdx showLineNumbers title="実際の Alignment"
| Property | Type | Required | Default |
| :--- | :--- | :---: | ---: |
| `name` | `string` | Yes | - |
| `enabled` | `boolean` | No | `true` |
| `limit` | `number` | No | `20` |
| `timeout` | `number` | No | `5000` |
```

**デモ**

| Property  | Type      | Required | Default |
| :-------- | :-------- | :------: | ------: |
| `name`    | `string`  |    Yes   |       - |
| `enabled` | `boolean` |    No    |  `true` |
| `limit`   | `number`  |    No    |    `20` |
| `timeout` | `number`  |    No    |  `5000` |

## 8. Table 内のインラインコード

技術ドキュメントで最もよく使われる table の使い方の1つは、cell の中にインラインコードを配置することです。

**コード**

```mdx showLineNumbers title="インラインコード"
| Property | Type | Description |
| --- | --- | --- |
| `id` | `string` | Unique identifier |
| `createdAt` | `Date` | Creation timestamp |
| `isActive` | `boolean` | Whether the user is active |
```

**デモ**

| Property    | Type      | Description                |
| ----------- | --------- | -------------------------- |
| `id`        | `string`  | Unique identifier          |
| `createdAt` | `Date`    | Creation timestamp         |
| `isActive`  | `boolean` | Whether the user is active |

技術ドキュメントでは、次のようなものにインラインコードを使うべきです。

* Variable name。
* Function name。
* Class name。
* File name。
* Command。
* API parameter。
* Environment variable。
* Type。
* HTTP method。
* URL path。

例:

```md
`DATABASE_URL`
`npm run dev`
`UserRepository`
`POST`
`/api/users`
```

| --- | --- | --- |
| **Authentication** | **Supported** | OAuth2 authentication |

**デモ**

| Feature            | Status        | Description             |
| ------------------ | ------------- | ----------------------- |
| **Authentication** | **Supported** | OAuth2 authentication   |
| *Analytics*        | Planned       | Usage analytics         |
| ~~Legacy API~~     | Deprecated    | Use the new API instead |

table の中で太字を乱用すべきではありません。すべてが太字になっていると、hierarchy がなくなってしまいます。

## 12. 空の値を持つ Table

**コード**

```mdx showLineNumbers title="Empty Cell"

| --- | :---: | --- |
| `id` | Yes | - |
| `name` | Yes | - |
| `avatar` | No | |
```

| -------- | :------: | ------- |
| `id`     |    Yes   | -       |
| `name`   |    Yes   | -       |

## 13. 複数行のテキストを持つ Table

cell にはかなり長いテキストを含めることができます。

**コード**

```mdx showLineNumbers title="Long Description"
| Property | Description |
| --- | --- |
| `timeout` | Determines how long the client waits for a response before the request is considered failed. |
| `retry` | Determines whether the request should automatically be retried after a temporary network failure. |
```

**デモ**

| Property  | Description                                                                                        |
| --------- | --------------------------------------------------------------------------------------------------- |
| `timeout` | Determines how long the client waits for a response before the request is considered failed.        |
| `retry`   | Determines whether the request should automatically be retried after a temporary network failure.   |

ただし、description が長すぎると、table が読みにくくなることがあります。

そのような場合は、詳細な説明を table の外に移すことを検討してください。

例:

| Property  | Type      | Required |
| --------- | --------- | -------- |
| `timeout` | `number`  | No       |
| `retry`   | `boolean` | No       |

table の後に:

> `timeout` determines how long the client waits for a response before the request fails.

この方法の方が、通常は読みやすくなります。

## 20. 内容に `|` 記号を含む Table

よくある問題として、cell の内容に `|` 文字が含まれる場合があります。

TypeScript の union type の例:

```ts
"asc" | "desc"
```

そのまま書くと:

```md
| Type |
| --- |
| `"asc" | "desc"` |
```

`|` 文字が Markdown parser によって table の separator と解釈されてしまう可能性があります。

:::danger
`|` のエスケープを忘れると、table の構造が誤って解析されます。多くの場合、column がずれたり、その下の table 全体が壊れたりします。source は一見有効に見えるため、render して初めて問題が分かる、発見しにくいバグです。
:::

安全な方法はエスケープすることです。

**コード**

```mdx showLineNumbers title="Escape Pipe Character"
| Parameter | Type |
| --- | --- |
| `order` | `"asc" \| "desc"` |
```

**デモ**

| Parameter | Type              |
| --------- | ------------------ |
| `order`   | `"asc" \| "desc"`  |

`|` 文字を cell の内容として表示する必要がある場合は、次のように書きます。

```md
\|
```

## 21. HTML を含む Table

MDX/Markdown 環境は、parser や設定によって HTML をサポートできる場合があります。

例:

```md
| Name | Description |
| --- | --- |
| **API** | Backend API |
```

特別な理由がない限り、通常は HTML よりも Markdown 構文を優先すべきです。

スタイリングのためだけに、シンプルな Markdown Table を HTML `<table>` に変えるべきではありません。

カスタムの挙動や複雑な構造が必要な場合は、専用の component を作ることを検討してください。

## 22. モバイルでの Table のレスポンシブ対応

これはドキュメントサイトにとって非常に重要な問題です。

column が多い table:

| Property  | Type      | Required | Default | Description     | Example |
| --------- | --------- | -------- | ------- | ---------------- | ------- |
| `timeout` | `number`  | No       | `5000`  | Request timeout  | `3000`  |
| `retry`   | `boolean` | No       | `false` | Retry request    | `true`  |

は、モバイル画面の幅を超えてしまうことがあります。

すべての column を無理に縮めて、テキストが読みにくくなるレベルまで圧縮すべきではありません。

一般的な方法は、table を横方向にスクロールできるようにすることです。

CSS の例:

```css
table {
    width: 100%;
}

.table-wrapper {
    overflow-x: auto;
}
```

ドキュメントシステムにすでに responsive table を処理する CSS がある場合は、table ごとに手動で wrapper を追加する必要はありません。

:::caution[警告]
column の多い table は、実際に確認しないとモバイルではみ出したりレイアウトが崩れたりしやすいです。desktop で見ただけで、小さい画面でも問題ないと決めつけないでください。
:::

table を確認すべき環境は次のとおりです。

* Desktop。
* Tablet。
* Mobile。
* Dark mode。
* ブラウザの大きなズーム。

---

## 23. 幅の広すぎる Table を作らない

column が多すぎる table は、多くの場合 information architecture が良くないサインです。

例:

| Name | Type | Required | Default | Description | Example | Version | Platform | Notes | Status |
| ---- | ---- | -------- | ------- | ----------- | ------- | ------- | -------- | ----- | ------ |

この table には多くの情報を詰め込めますが、読者にとっては追いにくくなります。

次のように分割できます。

### Parameters

| Name      | Type      | Required | Default |
| --------- | --------- | -------- | ------- |
| `timeout` | `number`  | No       | `5000`  |
| `retry`   | `boolean` | No       | `false` |

### Compatibility

| Version | Platform | Status    |
| ------- | -------- | --------- |
| v1      | Web      | Supported |
| v2      | Web      | Supported |

### Description

各 parameter の詳細な説明は、以下のセクションで行います。

情報を複数の小さな table に分けるほうが、1つの巨大な table よりも通常は優れています。

## 24. Table は Heading の代わりにならない

table を使って document の heading 構造を置き換えるべきではありません。

良くない例:

| Section        | Content |
| -------------- | ------- |
| Authentication | ...     |
| Configuration  | ...     |
| Deployment     | ...     |

それがドキュメントの構造であれば、次のようにすべきです。

```md
## Authentication

## Configuration

## Deployment
```

table は**構造化されたデータ**のために使うべきであり、ページ全体の layout を作るために使うものではありません。

---

## 25. Table を Layout として使わない

Markdown Table は layout system ではありません。

次のようなことはすべきではありません。

```md
| Left Content | Right Content |
| --- | --- |
| Text... | Text... |
```

ページに2カラムの layout を作るためだけにこれを使うべきではありません。

layout が必要な場合は:

* Use CSS。
* Use component。
* Use grid/flex。
* Use MDX component。

table は**tabular data**を表すべきものです。

:::caution[警告]
table を layout として使うのは、他の場所(Word、Notion、Confluence)からコンテンツを移行する際によく見られるアンチパターンです。このような table は、そのまま残さずに component や CSS layout に置き換えてください。
:::

---

## 26. Markdown Table をいつ使うべきか

Markdown Table は次のような場合に適しています。

* データに明確な行と列がある。
* 各 row が同じ構造を持つ。
* 読者が比較する必要がある。
* インタラクションが不要。
* sorting が不要。
* filtering が不要。
* pagination が不要。
* 複雑な nested component が不要。

非常に適した例:

```md
| Property | Type | Required |
| --- | --- | :---: |
| `id` | `string` | Yes |
| `name` | `string` | Yes |
```

---

## 27. Markdown Table を使うべきでない場合

table に次のようなものが必要な場合:

* Sorting。
* Filtering。
* Pagination。
* Search。
* Checkbox。
* Button。
* Dropdown。
* Expand/collapse。
* Nested component。
* Dynamic data。
* API data。
* Custom interaction。

その場合、Markdown Table はもはや理想的な選択肢ではありません。

代わりに component を作るべきです。

例:

```mdx
<DataTable
    data={users}
    sortable
    searchable
/>
```

この方法は、MDX が Markdown と component を組み合わせられるため、MDX により適しています。

## 28. 技術ドキュメントにおける Table 作成のルール

良い table は、いくつかのシンプルな原則に従うべきです。

### Header を短く保つ

良い例:

| Property | Type | Required |
| -------- | ---- | -------- |

良くない例:

| The name of the property | The type of this property | Whether the property is required or not |
| ------------------------ | -------------------------- | ----------------------------------------- |

### technical identifier にはインラインコードを使う

良い例:

| Property | Type     |
| -------- | -------- |
| `userId` | `string` |

次の代わりに:

| Property | Type   |
| -------- | ------ |
| userId   | string |

### status は中央揃え

| Feature | Status |
| ------- | :----: |
| Login   |    ✅   |

### 数値は右揃え

| Requests |   |
| -------: | - |
|     1000 |   |

### 情報を詰め込みすぎない

table が広くなりすぎた場合は、複数の table に分割してください。

### table を layout として使わない

table はデータであり、CSS layout ではありません。

## 29. API Documentation のための完全な Table 例

以下は、技術ドキュメントで実際に使われる方法に最も近い例です。

**コード**

```mdx showLineNumbers title="API Parameters"
| Parameter | Type | Required | Default | Description |
| :--- | :---: | :---: | :---: | :--- |
| `page` | `number` | No | `1` | Page number. Must be greater than `0`. |
| `limit` | `number` | No | `20` | Number of records returned per page. |
| `sort` | `string` | No | `createdAt` | Field used to sort the result. |
| `order` | `"asc" \| "desc"` | No | `"desc"` | Sort direction. |
| `search` | `string` | No | `-` | Search keyword. |
```

**デモ**

| Parameter |        Type       | Required |   Default   | Description                            |
| :-------- | :---------------: | :------: | :---------: | :--------------------------------------- |
| `page`    |      `number`     |    No    |     `1`     | Page number. Must be greater than `0`.   |
| `limit`   |      `number`     |    No    |     `20`    | Number of records returned per page.     |
| `sort`    |      `string`     |    No    | `createdAt` | Field used to sort the result.           |
| `order`   | `"asc" \| "desc"` |    No    |   `"desc"`  | Sort direction.                          |
| `search`  |      `string`     |    No    |     `-`     | Search keyword.                          |

これは API documentation で頻繁に使うべきパターンの1つです: **Parameter → Type → Required → Default → Description**。

## 30. Table と Code Block の組み合わせ

table にすべての情報を含める必要はありません。

良いパターンは、table で概要を示し、その後 code block で詳細を説明することです。

**コード**

```mdx showLineNumbers title="Overview"
| Property | Type | Required |
| --- | --- | :---: |
| `host` | `string` | Yes |
| `port` | `number` | No |
| `secure` | `boolean` | No |
```

**デモ**

| Property | Type      | Required |
| -------- | --------- | :------: |
| `host`   | `string`  |    Yes   |
| `port`   | `number`  |    No    |
| `secure` | `boolean` |    No    |

その後:

````mdx showLineNumbers title="Configuration"
```ts
const config = {
    host: "localhost",
    port: 3000,
    secure: false,
};
```
````

この方法は、読者が implementation の詳細に入る前に、素早く overview を把握するのに役立ちます。

## 31. Table を書く前のチェックリスト

table を作成する前に、自分自身に問いかけてください。

* データは本当に行/列の形式か?
* 読者は row を比較する必要があるか?
* header は短く明確か?
* 各 row は同じ数の column を持っているか?
* どの column を左揃えにすべきか?
* どの column を中央揃えにすべきか?
* どの column を右揃えにすべきか?
* technical identifiers にはインラインコードを使ったか?
* table は広すぎないか?
* モバイルで読めるか?
* Markdown Table の代わりに component が必要ではないか?

答えが Yes であれば、Markdown Table は多くの場合適切な選択です。

## 32. `^^` による Row の結合(Rowspan)

標準の Markdown Table は **rowspan をサポートしていません**——1つの cell が複数の row にまたがるためのネイティブな構文は存在しません。

このドキュメントでは、row の先頭にある cell の内容がちょうど2文字の `^^` である場合、それは空欄ではなく「同じ column の1つ上の cell と結合する」という意味として解釈されます。

:::danger[よくある間違い]
結合したい cell には `^^` のみを記述してください。同じ cell 内に空白や他の文字を追加しないでください(例: `^^ `、`^^abc`)。追加すると、その cell は結合マーカーではなく通常のテキストとして扱われます。
:::

**ソースコード**

```mdx showLineNumbers title="^^ による Rowspan"
| 機能 | サブ機能 | ステータス |
| --- | --- | --- |
| ログイン | Vlive アカウント | 完了 |
| ^^ | Google | 完了 |
| ^^ | Facebook | 完了 |
```

**プレビュー**

| 機能 | サブ機能 | ステータス |
| --- | --- | --- |
| ログイン | Vlive アカウント | 完了 |
| ^^ | Google | 完了 |
| ^^ | Facebook | 完了 |

レンダリングされた HTML では、`ログイン` は1つの cell となり、その `rowspan` は同じ column で連続して `^^` を使用している row の数と等しくなります。それらの `^^` cell は、それぞれの row にはもう存在しません。

使用する際の注意点:

* `^^` は**直上**の cell としか結合しません。別の値によってすでに区切られた row をまたいで結合することはできません。
* `^^` は最初の column に限らず、どの column でも使用できます。
* header の直後、つまりデータの最初の row では `^^` を使用しないでください。上に結合できる cell が存在しないためです。
* row が本当に同じ論理グループに属している場合にのみ使用してください(例: 1つの親機能に属する複数のサブ機能)。無関係な table の表示を「取り繕う」ために使用しないでください。

## まとめ

MDX における table は、実質的に Markdown Table の構文を使用しており、通常のケースでは専用の component は必要ありません。

基本構造:

```mdx showLineNumbers title="Basic Table"
| Column 1 | Column 2 | Column 3 |
| --- | --- | --- |
| Value | Value | Value |
| Value | Value | Value |
```

最も重要な原則:

1. **Header は明確でなければならない。**
2. **各 row は同じ数の column を持つべきである。**
3. **Text は通常左揃えにする。**
4. **Status/boolean は通常中央揃えにする。**
5. **Number は通常右揃えにする。**
6. **Property 名、type、command、API parameter にはインラインコードを使うべきである。**
7. **幅が広すぎる table は分割するか、horizontal scrolling をサポートすべきである。**
8. **table を layout として使わない。**
9. **複雑な interaction が必要なデータには Markdown Table を使わない。**
10. **技術ドキュメントでは、短く、構造化されていて、スキャンしやすい table を優先すべきである。**

良い table とは、最も多くの情報を詰め込んだ table ではなく、読者が**必要な情報を最も速く見つけられる**table のことです。
