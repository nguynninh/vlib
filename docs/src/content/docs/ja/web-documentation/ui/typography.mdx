タイポグラフィは、あらゆるドキュメントページの基礎です。テーブルやコールアウト、コードブロックを考える前に、内容の大部分は見出し・段落・基本的なテキスト装飾で構成されています。

内容が正しくてもタイポグラフィが乱れているページ——見出しのレベルが誤っている、太字が多用されすぎている、段落が長すぎるなど——では、読者が情報を受け取りにくくなります。

例えば、構造のない長い文章を書く代わりに：

```md title="構造がない例"
パッケージをインストールするには npm install を実行し、その後 config.json という設定ファイルを作成する必要があります。重要なのは正しい API key を入力することで、そうしないとアプリケーションが起動しません。
```

見出し・段落・インラインコードを使って明確に分けるべきです。

## 1. 見出し

見出しはコンテンツを階層化するために使います。Markdown では `#` を使って見出しを作成し、`#` の数が見出しのレベルに対応します。

**コード**

```md showLineNumbers title="見出しのレベル"
# 見出し 1
## 見出し 2
### 見出し 3
#### 見出し 4
```

Starlight では、frontmatter で宣言されたページの `title` がすでに見出し 1 の役割を果たしています。そのため、ページ本文の見出しは `##`（見出し 2）以下から始めるべきです。

```mdx title="Frontmatter"
---
title: "ページ名"
---
```

:::caution[警告]
Starlight の MDX コンテンツ内では `#`（見出し 1）を使用しないでください。ページにはすでに見出し 1 の役割を果たす title が存在するためです。本文にさらに `#` を追加すると、同一ページ内に 2 つの見出し 1 が生じ、アウトライン構造や SEO を混乱させます。
:::

### 見出しレベルの順序

見出しは正しい階層順序で使用し、レベルを飛ばさないようにします。

推奨されない例：

```md title="見出しレベルを飛ばす"
## セクション
#### サブセクション
```

`##` から `###` を飛ばして `####` に直接ジャンプしています。

推奨される例：

```md title="正しい見出しの順序"
## セクション
### サブセクション
```

### 見出しは簡潔にする

良い例：

```md
## ユーザー認証
```

良くない例：

```md
## このシステムにおけるユーザー認証の仕組みと、それが重要である理由について
```

見出しが長すぎると目次（Table of Contents）の効果が薄れ、読者が素早く見出しをスキャンしにくくなります。

## 2. 段落

段落は通常のテキストブロックで、空行によって区切られます。

**コード**

```md showLineNumbers title="段落"
これは最初の段落です。

これは 2 番目の段落です。
```

**実行結果**

これは最初の段落です。

これは 2 番目の段落です。

:::caution[警告]
2 つの段落の間に空行がないと、Markdown はそれらを 1 つの段落として結合してしまい、別々の段落として扱われません。
:::

### 段落は短くする

技術文書では、1 つの段落は 1 つの内容に集中させ、通常 3〜4 文以内に収めるべきです。

複数の異なる要点を 1 つの長い段落に詰め込まないでください。複数の項目がある場合は、段落に無理に詰め込むのではなく、リストやテーブルを使用しましょう。

---

## 3. 太字

太字は重要な単語やフレーズを強調するために使われ、`**` を 2 つ使って作成します。

**コード**

```md showLineNumbers title="太字"
この API を呼び出す際、`timeout` パラメーターは**必須**です。
```

**実行結果**

この API を呼び出す際、`timeout` パラメーターは**必須**です。

:::caution[警告]
同じ段落内であまりに多くの単語を太字にしないでください。すべてが太字になると、何も目立たなくなり、太字の強調効果が失われます。
:::

---

## 4. 斜体

斜体は `*` または `_` を 1 つ使って作成し、専門用語や固有名詞、軽い強調によく使われます。

**コード**

```md showLineNumbers title="斜体"
Git では、この操作は *rebase* と呼ばれます。
```

**実行結果**

Git では、この操作は *rebase* と呼ばれます。

太字と斜体は `***` を 3 つ使うことで組み合わせられます。

**コード**

```md
この警告は***非常に重要***です。
```

**実行結果**

この警告は***非常に重要***です。

---

## 5. 取り消し線

取り消し線は `~~` を 2 つ使って作成し、古くなった、または適用されなくなった内容を示すために使います。

**コード**

```md showLineNumbers title="取り消し線"
~~`getUserById`~~ は非推奨です。代わりに `findUserById` を使用してください。
```

**実行結果**

~~`getUserById`~~ は非推奨です。代わりに `findUserById` を使用してください。

---

## 6. インラインコード

インラインコードはバッククォート `` ` `` を使って作成し、文中に登場する変数名、関数名、ファイル名、コマンド、技術的な値などに使います。

**コード**

```md showLineNumbers title="インラインコード"
`npm run build` を実行すると、`dist/` フォルダにファイルが生成されます。
```

**実行結果**

`npm run build` を実行すると、`dist/` フォルダにファイルが生成されます。

次のような場合にインラインコードを使うべきです。

* 変数名、関数名、クラス名。
* ファイル名、ディレクトリ名。
* ターミナルコマンド。
* 具体的な値（`true`、`null`、`200`）。
* 環境変数名。

:::tip
インラインコードの中にバッククォート自体を含める必要がある場合は、二重のバッククォートで囲みます: `` `code` ``。
:::

## 7. 順不同リスト

順不同リストは、行頭の `-`、`*`、`+` のいずれかで作成します。

**コード**

```md showLineNumbers title="順不同リスト"
* 依存関係をインストールする。
* 環境を設定する。
* マイグレーションを実行する。
```

**実行結果**

* 依存関係をインストールする。
* 環境を設定する。
* マイグレーションを実行する。

:::tip
記号は 1 種類（`-`、`*`、`+` のいずれか）を選び、ドキュメント全体で一貫して使用することで、ソースコードが読みやすくなります。
:::

### ネストされたリスト

**コード**

```md showLineNumbers title="ネストされたリスト"
* フロントエンド
    * React
    * Vue
* バックエンド
    * Node.js
    * Spring Boot
```

**実行結果**

* フロントエンド
    * React
    * Vue
* バックエンド
    * Node.js
    * Spring Boot

ネストされた項目は、レベルごとにスペース 4 個（またはタブ 1 個）でインデントし、パーサーが階層を誤って解釈しないようにします。

---

## 8. 順序付きリスト

順序付きリストは、数字の後に `.` を付けて作成します。

**コード**

```md showLineNumbers title="順序付きリスト"
1. リポジトリをクローンする。
2. 依存関係をインストールする。
3. アプリケーションを実行する。
```

**実行結果**

1. リポジトリをクローンする。
2. 依存関係をインストールする。
3. アプリケーションを実行する。

:::note
Markdown はレンダリング時に番号を自動的に振り直すため、ソース内で `1. 1. 1.` と書いても、表示結果は `1. 2. 3.` になります。ただし、ソースの読みやすさのために正しい番号を書いておくことをお勧めします。
:::

### 順不同ではなく順序付きリストを使うべき場合

| 状況                                  | リストの種類 |
| -------------------------------------- | :----------: |
| 順番通りに実行しなければならない手順  | 順序付き     |
| 順番が重要でないリスト                | 順不同       |

項目の順序を変えると結果が変わる場合（例：インストール手順）は、順序付きリストを使用します。

## 9. タスクリスト

一部の Markdown フレーバー（Starlight がサポートする GitHub-Flavored Markdown を含む）では、リスト内にチェックボックスを使用できます。

**コード**

```md showLineNumbers title="タスクリスト"
- [x] API エンドポイントを実装する。
- [x] 単体テストを書く。
- [ ] ドキュメントを書く。
```

**実行結果**

- [x] API エンドポイントを実装する。
- [x] 単体テストを書く。
- [ ] ドキュメントを書く。

タスクリストは進捗チェックリストに適しており、より複雑なステータステーブルの代わりに使うべきではありません。

## 10. 引用

引用は行頭の `>` を使って作成し、コールアウトよりも控えめなレベルで、引用や軽い強調を行うために使います。

**コード**

```md showLineNumbers title="引用"
> `timeout` は、リクエストが失敗と判断されるまでにクライアントがレスポンスを待つ最大時間を定義します。
```

**実行結果**

> `timeout` は、リクエストが失敗と判断されるまでにクライアントがレスポンスを待つ最大時間を定義します。

### 引用とコールアウトの違い

| コンポーネント | 目的                                         |
| -------------- | ---------------------------------------------- |
| 引用           | 引用や補足説明で、強く目立たせる必要がない場合 |
| コールアウト   | 読者の注意を引く必要がある警告や注意事項       |

引用の代わりに `note`、`tip`、`caution`、`danger` のいずれを使うべきかについては、[コールアウト](/web-documentation/ui/callout)を参照してください。

引用は `>` を複数使うことでネストできます。

**コード**

```md
> 元の引用内容。
>
> > その引用に対する補足コメント。
```

**実行結果**

> 元の引用内容。
>
> > その引用に対する補足コメント。

---

## 11. 水平線

水平線は、`-`、`*`、`_` のいずれかを 3 つ、独立した行に配置して作成し、大きなコンテンツ部分を区切るために使います。

**コード**

```md
---
```

このドキュメントでは、大きなセクション（`## 1.`、`## 2.` など）を区切るために水平線を使用しており、読者が各部分の境界を把握しやすくなっています。

:::caution[警告]
ファイルの先頭、つまり前に何のコンテンツもない状態で `---` を配置すると、一部の Markdown パーサー（Astro/Starlight の frontmatter を含む）はそれを frontmatter の境界と誤認する可能性があります。`---` を水平線として使うのは、frontmatter の後、本文の途中のみにしてください。
:::

## 12. リンク

リンクは `[テキスト](url)` という構文を使います。

**コード**

```md showLineNumbers title="リンク"
表形式のデータの表現方法については[テーブル](/web-documentation/ui/table)を参照してください。
```

**実行結果**

表形式のデータの表現方法については[テーブル](/web-documentation/ui/table)を参照してください。

### 内部リンクと外部リンク

| リンクの種類 | 例                                        |
| ------------ | ------------------------------------------- |
| 内部         | `[テーブル](/web-documentation/ui/table)`  |
| 外部         | `[Astro](https://astro.build/)`            |

:::tip
内部リンクには、完全なドメインをハードコーディングするのではなく、サイト内の相対パス（`/web-documentation/...`）を使用しましょう。そうすればドメインを変更したり、ステージング環境で実行したりしてもリンクが機能し続けます。
:::

### リンクのテキストは明確に説明する

良くない例：

```md
詳細は[こちら](/web-documentation/ui/table)を参照してください。
```

良い例：

```md
[テーブルの表現方法](/web-documentation/ui/table)を参照してください。
```

説明的なテキストは、読者（およびスクリーンリーダーなどのアクセシビリティツール）が、周囲の文脈を読まなくてもリンクの行き先を理解する助けになります。

---

## 13. 画像

画像はリンクと似た構文を使い、先頭に `!` を付けます。

**コード**

```md
![システムアーキテクチャ図](/images/architecture.png)
```

`[]` 内のテキストは **alt テキスト** で、スクリーンリーダーに画像の内容を説明し、画像の読み込みに失敗した際に表示されます。

:::caution[警告]
alt テキストを空（`![]()`）にしたり、`![image]()` のように一般的すぎる内容にしたりしないでください。alt テキストは画像の内容を正確に説明する必要があり、アクセシビリティにおいて特に重要です。
:::

## 14. 段落内での改行

Markdown はデフォルトで、同じ段落内の単純な改行を**無視**します。

**コード**

```md
1 行目。
2 行目。
```

**実行結果**

1 行目。
2 行目。

上記の 2 行は、レンダリング時に 1 つの段落として結合されます。強制的に改行させるには、行末に半角スペースを 2 つ追加するか、`<br />` タグを使用します。

**コード**

```md
1 行目。<br />
2 行目。
```

**実行結果**

1 行目。<br />
2 行目。

:::tip
技術文書では、無理に改行させるのではなく、別々の段落に分けるかリストを使うことを優先しましょう。行末のスペースに依存する改行は、ファイルを再フォーマットした際に失われやすいためです。
:::

## 15. 特殊文字のエスケープ

Markdown ではいくつかの文字（`*`、`_`、`` ` ``、`#`、`|`、`[`、`]` など）が特別な意味を持ちます。これらを通常のテキストとして表示するには、`\` でエスケープする必要があります。

**コード**

```md showLineNumbers title="文字のエスケープ"
Markdown で太字にするには \*bold\* のように書きます。
```

**実行結果**

Markdown で太字にするには \*bold\* のように書きます。

`|` がテーブル内に現れる場合のエスケープ方法については、[`|` を含むテーブル](/web-documentation/ui/table#20-table-có-dấu--bên-trong-nội-dung)を参照してください。

## 16. 複数の装飾を組み合わせる

上記の装飾は、同じ段落内で組み合わせて使用できます。

**コード**

```md showLineNumbers title="装飾の組み合わせ"
**`apiKey`** パラメーターは*必須*です。指定がない場合、リクエストは `401` エラーを返します。詳細は[認証](/web-documentation/authentication)を参照してください。
```

**実行結果**

**`apiKey`** パラメーターは*必須*です。指定がない場合、リクエストは `401` エラーを返します。詳細は[認証](/web-documentation/ui/typography)を参照してください。

:::caution[警告]
同じ文の中で太字・斜体・コード・リンクなど、あまりに多くの装飾を組み合わせると読みにくくなります。本当に必要な部分だけを強調しましょう。
:::

## 17. どの装飾をいつ使うべきか

装飾を誤って選ぶと、読者が情報の重要度や種類を誤解してしまいます。

シンプルなルール：

| 目的                                        | 装飾           |
| --------------------------------------------- | -------------- |
| 変数、関数、ファイル、コマンド、技術的な値   | インラインコード |
| 重要な単語・フレーズの強調                    | **太字**       |
| 専門用語、固有名詞、軽い強調                  | *斜体*         |
| 古くなった、もう適用されない内容              | ~~取り消し線~~ |
| 軽い引用や補足説明                            | 引用           |
| 目立たせる必要のある警告や注意事項            | コールアウト   |
| 順番通りに実行する手順                        | 順序付きリスト |
| 順番が重要でないリスト                        | 順不同リスト   |
| 行・列形式のデータ                            | テーブル       |

:::tip
太字とインラインコードのどちらを使うべきか迷ったら、次のように自問してみてください。「これは具体的な技術的概念（変数名、コマンドなど）なのか、それとも単に文中で強調したい単語なのか？」技術的概念 → インラインコード。通常の強調 → 太字。
:::

## 18. 装飾を乱用しない

1 つの段落であまりに多くの異なる装飾を使うと、明瞭さが失われます。

推奨されない例：

```md
***注意***：`id` パラメーターは***`string`***型でなければならず、~~空にすることはできず~~、既存の id と**`重複してはいけません`**。
```

推奨される例：

```md
`id` パラメーターは `string` 型でなければならず、既存の `id` と重複してはいけません。

:::caution
`id` を空にすることはできません。
:::
```

このように、警告部分をコールアウトとして本文から切り離すことで、1 つの文にすべてを詰め込んで強調しようとするよりも読みやすくなります。

## 19. 典型的なドキュメントページの構成

上記のタイポグラフィ要素を組み合わせると、典型的な技術文書のページは次のような構成になります。

```md title="ドキュメントページの構成"
---
title: "ページ名"
description: "簡潔な説明"
---

ページ内容の簡単な紹介。

​```

対応する出力結果。

## まとめ

簡潔なまとめと重要な原則。
```

## 20. タイポグラフィを書く前のチェックリスト

ドキュメントページを仕上げる前に、次の点を自問してください。

* 見出しは `##` から始まり、正しい階層順序になっているか？
* 段落は十分に短く、それぞれが 1 つの内容に集中しているか？
* 太字が乱用されていないか？
* 変数名、関数名、ファイル名、コマンドはインラインコードとして表現されているか？
* 古くなった内容は、（参照を残す必要がある場合）完全に削除するのではなく取り消し線が使われているか？
* リンクのテキストは「こちら」ではなく、行き先を明確に説明しているか？
* 画像には内容を正確に説明する alt テキストが設定されているか？
* 特殊文字（`|`、`*`、`_` など）は必要な箇所でエスケープされているか？
* 文章のままにするのではなく、リストやテーブルに変換すべき段落はないか？
* 太字・斜体で無理に強調するのではなく、コールアウトを使うべき段落はないか？

## まとめ

タイポグラフィは、あらゆるドキュメントページの基礎となる層です。テーブル、コールアウト、Mermaid といったより複雑な要素を検討する前に、見出し・段落・基本的な装飾が正しく使われている必要があります。

最も重要な原則：

1. **本文中の見出しは `##` から始める**。`#` は使わない。ページの title がすでに見出し 1 の役割を果たしているため。
2. **見出しは正しい階層順序に従う**。レベルを飛ばさない。
3. **段落は簡潔にする**。それぞれが 1 つの内容に集中する。
4. **技術的なものはすべてインラインコードにする**：変数、関数、ファイル、コマンド、値。
5. **太字は選択的な強調に使う**。乱用しない。
6. **軽い内容には引用を、目立たせるべき警告にはコールアウトを使う。**
7. **リンクには明確な説明テキストが必要**。「こちら」は使わない。
8. **画像には内容を正確に説明する alt テキストが必要。**
9. **特殊文字は必要な箇所で正しくエスケープする。**
10. **構造化されたデータにはリストやテーブルを優先する**。冗長な文章は避ける。

タイポグラフィの良いドキュメントページとは、最も多くの装飾を使ったページではなく、読者が**最も速く必要な情報にたどり着けるページ**です。
