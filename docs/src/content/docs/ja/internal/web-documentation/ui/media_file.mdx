メディア＆ファイルは、テキストだけに頼らず技術ドキュメントをより視覚的にするための要素です。

ただし、ソースコードとは異なり、メディアファイル（画像、動画、音声、添付ファイル）は**プロジェクトに直接インポートしてはいけません**。すべてのメディアファイルは `vlib-storage` リポジトリの [GitHub Releases](https://github.com/nguynninh/vlib-storage/releases) にアップロードし、その asset のリンクを取得してドキュメント内で使用します。

:::danger[メディアファイルをプロジェクトに commit しない]
画像、動画、音声、添付ファイルを `src/assets` やプロジェクトの他のディレクトリに置いて Git に直接 commit してはいけません。メディアファイルはソースコードよりもはるかに容量が大きいことが多く、Git は commit されたすべてのファイルの履歴を、後で削除された場合でも永久に保持します。これによりリポジトリが恒久的に肥大化し、clone や CI/CD、新しいマシンでのプロジェクトオープンが遅くなります。
:::

代わりに、正しい手順は次のとおりです。

1. メディアファイルを GitHub の **Release** にアップロードする。
2. アップロードした asset のダウンロードリンク（`browser_download_url`）をコピーする。
3. ローカルファイルのパスの代わりに、そのリンクを MDX で使用する。

---

## 1. メディアの保存に GitHub Releases を使う理由

GitHub Releases では、バイナリファイル（**Assets**）をタグに添付でき、ソースコードの commit 履歴とは完全に分離されます。

| ファイルの保存方法              | リポジトリへの影響                          |
| ------------------------------- | ------------------------------------------- |
| `src/` に直接 commit する       | リポジトリが恒久的に肥大化し、clone が遅くなる |
| Git LFS を使う                  | 追加の設定が必要で、LFS の容量制限にも影響する |
| GitHub Releases にアップロードする | commit 履歴に影響せず、タグごとにバージョン管理できる |

そのため、このプロジェクトでは、ドキュメントで使用するすべてのメディアファイルの正式な保存先として GitHub Releases を採用しています。

:::note
メディアを保存するリポジトリは、ドキュメントサイトのソースコードを含むリポジトリとは分離された、ストレージ専用のリポジトリ（例: `vlib-storage`）である場合があります。新しい release を作成する前に、プロジェクトの現在の規約を確認してください。
:::

## 2. GitHub Releases にファイルをアップロードする

リポジトリの **Releases** ページで、release を作成または開き、**Assets** 部分にファイルをドラッグ＆ドロップします。

ドキュメントで使う asset を含む release の例:

| Asset             | サイズ | 用途                     |
| ------------------ | ---------: | ------------------------------ |
| `photo_demo.jpg`   |    2.73 MB | UI ページの説明用画像      |
| `video_demo.mp4`   |   56.2 MB  | 機能デモ動画           |

アップロード後、各 asset は次の形式の固定ダウンロードリンクを持ちます。

```text
https://github.com/<owner>/<repo>/releases/download/<tag>/<file-name>
```

例:

```text
BASE_STORAGE/v1.0.0/photo_demo.jpg
```

:::tip
**Assets** 部分でファイル名を右クリックし、**Copy link address** を選ぶことで正確なダウンロードリンクを取得できます。手入力によるパスの誤りを避けられます。
:::

### 完全なリンクの代わりに `BASE_STORAGE` 変数を使う

ダウンロードリンクのドメイン部分を MDX ファイルごとに貼り付ける代わりに、このプロジェクトでは環境変数 `BASE_STORAGE`（`.env`、`.env.development`、`.env.production` で宣言）を接頭辞として使用します。ドキュメントを書く際は、次のように書くだけで済みます。

```md
BASE_STORAGE/<tag>/<file-name>
```

ビルド時に、remark プラグインが `BASE_STORAGE` を環境変数の実際の値に自動的に置き換えます。例えば:

```bash title=".env.production"
BASE_STORAGE=BASE_STORAGE
```

:::tip
この仕組みにより、ドキュメント内のすべてのリンクを書き換えることなく、メディアの保存場所を変更できます（例えば別の CDN に切り替える、開発環境と本番環境で異なるストレージリポジトリを使うなど）。
:::

## 3. 画像・動画・音声の共通構文

画像、動画、音声はすべて**同じ Markdown image 構文**を使い、`<figure>`、`<a>`、`<img>`、`<video>`、`<audio>` などの HTML を手動で書く必要はありません。サイト側がリンク内のファイル拡張子を見て、画像・動画プレーヤー・音声プレーヤーのどれとして render するかを自動的に判断します。

**コード**

```mdx showLineNumbers title="GitHub Releases のリンクでメディアを挿入する"
![サイドバー、ヘッダー、メインコンテンツを含む Dashboard 画面](BASE_STORAGE/v1.0.0/photo_demo.jpg)
```

**プレビュー**

![サイドバー、ヘッダー、メインコンテンツを含む Dashboard 画面](BASE_STORAGE/v1.0.0/photo_demo.jpg)

構造は3つの部分からなります。

1. `!` 記号は、これが通常のリンクではなく、直接表示すべきメディアであることを示します。
2. `[説明]` は alt text（画像の場合）またはキャプション/内容説明（動画、音声の場合）で、アクセシビリティのために使われます。
3. `(Release のリンク)` は、アップロード済み asset のダウンロードリンクであり、プロジェクト内のファイルパスではありません。

通常のメディアでは、書き手が**自分で HTML を書く必要はありません**。サイト側が画像を拡大可能なプレビュー枠に自動で包み、動画を `<video controls preload="metadata">` に、音声を `<audio controls>` に変換します。

キャプションのデフォルトは `[]` 内の説明がそのまま使われます。別のキャプションにしたい場合は、リンクの後の title 部分に引用符で囲んで書きます。

### title 内の共通オプション

title 部分（リンクの後の引用符内）に置く短いオプションは、3種類すべてに共通して適用されます。

| したいこと | 書き方 |
| ----------- | ---- |
| 左揃え | `"left"` |
| 中央揃え | 空欄または `"center"` |
| 右揃え | `"right"` |
| 幅の制限（px） | `"600"` |
| 右揃えかつ幅の制限 | `"right 600"` |
| デフォルトと異なるキャプション | `"表示したいキャプション"` |
| キャプションを右揃え | `"right caption-right"` |

**コード**

```mdx showLineNumbers title="基本のメディア"
![内容の説明](BASE_STORAGE/<tag>/<file-name>)
```

```mdx showLineNumbers title="右揃えのメディア"
![内容の説明](BASE_STORAGE/<tag>/<file-name> "right")
```

```mdx showLineNumbers title="表示オプション付きのメディア"
![内容の説明](BASE_STORAGE/<tag>/<file-name> "right 600")
```

```mdx showLineNumbers title="キャプション付きのメディア"
![内容の説明](BASE_STORAGE/<tag>/<file-name> "説明1. より詳しい説明。")
```

動画には、16:9 のアスペクト比を固定するための2つの追加オプションがあります。下記の **動画** の項を参照してください。

### Alt text / 説明はオプションではない

`[]` 内に書く注釈は、スクリーンリーダー向けにメディアの内容を説明するものであり、メディアが読み込めなかったときにのみ表示されます。**メディアの下に表示されるタイトルではありません**。

避けるべき書き方:

```md
![](BASE_STORAGE/v1.0.0/photo_demo.jpg)
```

望ましい書き方:

```md
![サイドバー、ヘッダー、メインコンテンツを含む Dashboard 画面](BASE_STORAGE/v1.0.0/photo_demo.jpg)
```

:::caution[警告]
`image`、`video`、`pic` のような空または一般的すぎる alt text/説明は、スクリーンリーダー利用者が内容を理解できなくするだけでなく、ページの SEO 品質も低下させます。
:::

### アップロード前のファイル名の付け方

ファイルは Release にアップロードされてリンク経由で使われるため、ファイル名はより明確な意味を持たせる必要があります。多くのドキュメントページが古いリンクを参照するようになった後でファイル名を変更するのは非常に困難だからです。

| 良い例                       | 悪い例           |
| -------------------------- | -------------------- |
| `login-flow.png`           | `Screenshot 2026-01-01 at 10.23.45.png` |
| `checkout-payment-demo.mp4` | `video_final_final.mp4` |
| `order-notification-sound.mp3` | `Recording 2026-01-01.wav` |

:::caution[警告]
publish 後に Release 内の asset の名前を変更したり削除したりすると、その asset を参照しているすべてのドキュメントページのリンクが壊れます。`browser_download_url` はファイル名とタグに直接紐づいているためです。アップロード前に、最初から正しい名前を付けてください。
:::

### 注釈ボックス内のメディア

画像、動画、音声はいずれも、警告や補足と視覚的な説明を同時に行いたい場合に注釈ボックス内に配置でき、通常どおり Release のリンクを使用します。

**コード**

```mdx showLineNumbers title="メディアを含む注釈ボックス"
:::caution[新しいバージョンで UI が変更されました]
「保存」ボタンが右上から画面下部のバーへ移動しました。

![画面下部のバーに移動した新しい保存ボタンの位置](BASE_STORAGE/v1.0.0/video_demo2.jpg)
:::
```

**デモ**

:::caution[新しいバージョンで UI が変更されました]
「保存」ボタンが右上から画面下部のバーへ移動しました。

![画面下部のバーに移動した新しい保存ボタンの位置](BASE_STORAGE/v1.0.0/video_demo2.jpg "画面下部のバーに移動した新しい保存ボタンの位置")
:::

## 4. 画像

### 使用する画像の拡張子

以下のよく使われる画像拡張子のファイルにのみ Markdown のメディア構文を使用します。

| 拡張子 | 使うべき場面 |
| --------- | ------------ |
| `.png` | UI のスクリーンショット、透過領域のある画像 |
| `.jpg`, `.jpeg` | 実写画像、色数の多い画像 |
| `.webp` | 品質を保ちつつ容量を小さくしたい画像 |
| `.gif` | 音声のない非常に短いアニメーション |
| `.svg` | アイコン、ロゴ、シンプルなベクター図 |

`.bmp`、`.tiff`、`.heic` は、容量が大きい、またはブラウザの対応が不安定なため、Web ドキュメントには使用しません。

### 画像のサイズ

表示サイズを制御したい場合は、画像の title 部分に数値を書くだけで済みます（3節の**title 内の共通オプション**を参照）。`<img>` タグを手動で使う必要はありません。

:::caution[警告]
「見た目を整える」ためだけに大きな画像を `width` で無理に縮小すべきではありません。元の画像の解像度が高すぎる場合は、Release にアップロードする前にリサイズ・圧縮を行い、不要なページ読み込み時間の増加を避けてください。
:::

### 画像とキャプションの表示位置

画像はデフォルトで中央に揃えられます。位置を変えたい場合は、引用符内に `left`、`center`、`right` を追加するだけです。

**コード**

```mdx showLineNumbers title="画像とキャプションの位置揃え"
![サイドバー、ヘッダー、メインコンテンツを含む Dashboard 画面](BASE_STORAGE/v1.0.0/photo_demo.jpg "left caption-left")

![画面下部のバーに移動した新しい保存ボタンの位置](BASE_STORAGE/v1.0.0/video_demo2.jpg "right caption-right")
```

**デモ**

![サイドバー、ヘッダー、メインコンテンツを含む Dashboard 画面](BASE_STORAGE/v1.0.0/photo_demo.jpg "left caption-left")

![画面下部のバーに移動した新しい保存ボタンの位置](BASE_STORAGE/v1.0.0/video_demo2.jpg "right caption-right")

### Before / After の比較画像

**コード**

```mdx showLineNumbers title="Before / After の比較"
| Before | After |
| --- | --- |
| ![旧デザインの UI](BASE_STORAGE/v1.0.0/photo_demo.jpg) | ![新デザインの UI](BASE_STORAGE/v1.0.0/video_demo2.jpg) |
```

**デモ**

| Before | After |
| --- | --- |
| ![旧デザインの UI](BASE_STORAGE/v1.0.0/photo_demo.jpg "旧デザインの UI") | ![新デザインの UI](BASE_STORAGE/v1.0.0/video_demo2.jpg "新デザインの UI") |

画像を table 内に配置すると、読者はスクロールを行き来せずに直接比較できます。

## 5. 動画

動画は常に容量が大きいため、**必ず** Release にアップロードする必要があり、動画ファイルをプロジェクトに commit することは絶対に避けてください。挿入の構文は画像とまったく同じです（3節を参照）。サイト側がファイル拡張子（`.mp4`、`.webm`、`.mov`、`.ogg`）を見て、`controls` 付きの動画プレーヤーとして render します。

### 動画固有のオプション

3節の共通オプションに加えて、動画には 16:9 のアスペクト比を固定するための2つの追加オプションがあります。

| したいこと | 書き方 |
| ----------- | ---- |
| 720p、16:9 の動画フレーム | `"720p"` |
| 1080p、16:9 の動画フレーム | `"1080p"` |
| ファイルの元のアスペクト比を保持 | 空欄または `"auto"` |

```mdx showLineNumbers title="720p フレームの動画"
![動画の内容説明](BASE_STORAGE/<tag>/<file-name>.mp4 "720p")
```

```mdx showLineNumbers title="1080p フレームの動画"
![動画の内容説明](BASE_STORAGE/<tag>/<file-name>.mp4 "1080p")
```

動画プレーヤーには常に `controls` が付き、読者が必要に応じて一時停止・シーク・音量調整を行えます。サイト側は `preload="metadata"` も自動で使用するため、ページを開いた瞬間に動画全体が読み込まれることはありません。

:::caution[警告]
音声付きの自動再生動画をドキュメントで使わないでください。自動再生が必要な場合は、`muted` にした動画にのみ手動の HTML を使用してください。
:::

### 動画のサイズ

ドキュメント内で 640〜720px 程度でしか表示しない動画に、4K のファイルをアップロードすべきではありません。アップロード前にリサイズ・再エンコードを行い、ページの読み込み時間を短縮してください。

### 外部プラットフォームの動画

すでに外部プラットフォーム（YouTube、Vimeo）に存在する動画は、Release へ再アップロードせずに `<iframe>` で直接埋め込むことができます。

```mdx showLineNumbers title="YouTube から埋め込む動画"
<iframe
    width="720"
    height="405"
    src="https://www.youtube.com/embed/VIDEO_ID"
    title="プロジェクトのインストール手順"
    allowfullscreen
></iframe>
```

## 6. 音声

音声も画像や動画と同様に、事前に Release へアップロードする必要があり、プロジェクトに直接 commit してはいけません。挿入の構文は画像・動画とまったく同じです（3節を参照）。サイト側がファイル拡張子（`.mp3`、`.wav`、`.ogg`）を見て、`controls` 付きの音声プレーヤーとして render します。音声は再生用のプレーヤーのみを表示し、画像のような拡大機能はなく、動画のようなフレーム固定オプションにも対応していません。

音声プレーヤーには常に `controls` が付き、自動再生せず、読者が自分でボタンを押して聴く形になります。

:::caution[警告]
ドキュメントで音声の自動再生（`autoplay`）を使わないでください。読者は複数のページを同時に開いていることがあり、自動再生の音声は体験を妨げ、すぐに止めるのが難しくなります。
:::

## 7. インタラクション説明用の GIF

GIF は画像と同様に直接表示され、音声のない短い操作の説明に適しています。

**コード**

```mdx showLineNumbers title="説明用の GIF"
![ドキュメント内の操作を示すデモ GIF](BASE_STORAGE/v1.0.0/gif_demo.gif)
```

**プレビュー**

![ドキュメント内の操作を示すデモ GIF](BASE_STORAGE/v1.0.0/gif_demo.gif)

:::caution[警告]
GIF は効率よく圧縮できないため、適切にエンコードされた動画よりも容量が大きくなることがよくあります。数秒を超えるデモの場合、`controls` 付きの MP4 動画のほうが GIF よりも良い選択であることが多く、他の動画と同様に Release へアップロードすべきです。
:::

## 8. PDF

PDF は画像、動画、音声と同じ Markdown image 構文を使います。サイト側が `.pdf` 拡張子を見て、PDF アイコン付きのファイルカードとファイルを開くリンクとして render します。

**コード**

```mdx showLineNumbers title="PDF を直接表示する"
![SDK Integration Documentation For Android.pdf](BASE_STORAGE/v1.0.0/pdf_demo.pdf)
```

```mdx showLineNumbers title="ダウンロードボタン付きの PDF"
![SDK Integration Documentation For Android.pdf](BASE_STORAGE/v1.0.0/pdf_demo.pdf download)
```

**プレビュー**

![SDK Integration Documentation For Android.pdf](BASE_STORAGE/v1.0.0/pdf_demo.pdf download)

リンクのテキストは `[]` 内の説明から取られます。PDF はコンパクトなファイルカードとして表示され、ファイル名をクリックすると PDF のプレビューが開きます。**ダウンロード** ボタンも表示したい場合は、PDF のリンクの後に `download` を追加します。

## 9. その他のメディア

`.zip`、`.xlsx`、`.docx`、デザインファイルやテンプレートなどの形式はインラインで埋め込むべきではありません。ダウンロードリンクを置き、読者が適切なソフトウェアでダウンロードして開く必要があることを明記してください。

`.zip`、`.xlsx`、`.docx`、`.psd`、`.fig` や社内テンプレートなど、Web で良好に表示できないファイルは、ダウンロードリンクとしてのみ配置すべきです。

**コード**

```mdx showLineNumbers title="ダウンロードが必要なファイル"
![レポートテンプレートをダウンロード (.xlsx)](BASE_STORAGE/v1.0.0/report-template.xlsx)

![デザインリソース一式をダウンロード (.zip)](BASE_STORAGE/v1.0.0/design-assets.zip)
```

読者がクリックする前にファイル形式を把握できるよう、`(.xlsx)` や `(.zip)` のように、リンクのテキストにファイル形式を明記することをおすすめします。

## 10. 管理と最適化

### Release タグによるメディアのバージョン管理

各 asset は特定の Release タグに紐づいているため、メディアのバージョン管理はソースコードのバージョン管理と同じ方法で行えます。

| Release タグ | 変更内容                     |
| ------------ | --------------------------------------- |
| `v1.0.0`     | 初期の画像・動画デモ一式           |
| `v1.1.0`     | 新しい UI に合わせたスクリーンショットの更新 |

製品の UI が変更されてスクリーンショットの更新が必要な場合は、既存の Release 内のファイルを置き換えるのではなく、新しいタグの Release を作成してください。これにより、旧バージョンのドキュメントページから参照されているリンクが壊れるのを防げます。

:::note
古いドキュメント（例えば `v1.0.0` のドキュメント）で引き続き旧デザインの UI を正しく表示する必要がある場合は、そのページでは Release `v1.0.0` の asset リンクをそのまま維持し、新しい内容にのみ Release `v1.1.0` の asset を使用してください。
:::

### 使用すべきファイル形式

| 形式 | 適した用途                          |
| --------- | -------------------------------------- |
| `.png`    | スクリーンショット、透過領域のある画像、UI |
| `.jpg`    | 実写画像、色数の多い画像 |
| `.svg`    | アイコン、ロゴ、シンプルなベクター図     |
| `.webp`   | 品質を保ちつつ容量を小さくしたい画像 |
| `.gif`    | 音声のない短いアニメーション      |
| `.mp4`    | デモ動画、インタラクションの説明        |

`.bmp` や `.tiff` は容量が大きく、ブラウザの対応も最適でないため使用しないでください。

### アップロード前のファイル最適化

ファイルは読者がページを開くたびに GitHub Releases のリンクから読み込まれるため、ファイルの容量はドキュメントの読み込み速度に直接影響します。

アップロード前に適用すべきいくつかの原則:

* 実際に表示する必要のあるサイズに画像をリサイズし、Retina/4K 画面から撮った元のスクリーンショットをそのまま使わない。
* アップロード前に画像を圧縮する。
* 透過が不要な画像には `.webp` を優先する。
* デモ動画は 1〜2 分以内に収め、適切なビットレートでエンコードする。

### 説明用の画像には前後の文脈を添える

Release から取得した画像であっても、他のソースから取得した画像であっても、導入文や説明なしに画像だけを単独で置くべきではありません。

良くない例:

```md
![](BASE_STORAGE/v1.0.0/error-screen.png)
```

望ましい例:

```md
トークンの期限切れによりリクエストが失敗すると、アプリは次のエラー画面を表示します。

![「Session expired」と「再ログイン」ボタンが表示されたエラー画面](BASE_STORAGE/v1.0.0/error-screen.png)

ユーザーは**再ログイン**を押して新しいトークンを取得する必要があります。
```

### 重要なテキストを画像だけで表現しない

URL、コマンド、設定値などのテキストが画像の中にしか存在しない場合、読者はそれをコピーできず、ドキュメント内検索でもその内容を見つけられません。

望ましい方法 — 画像と、それに対応する実際のテキストの両方を用意する:

````md
依存関係をインストールするには、次のコマンドを実行します。

```bash
npm install
```

![npm install 実行後のターミナルの状態](BASE_STORAGE/v1.0.0/install-command.png)
````

:::caution[警告]
重要なコマンドや設定を含む画像に対応するテキストがないのは、スクリーンショットを急いでドキュメントに貼り付ける際によくある間違いです。読者は手動で入力し直す必要が生じ、ミスが起こりやすくなります。
:::

### メディアやファイルを挿入する前のチェックリスト

画像、動画、音声、添付ファイルを追加する前に、次の点を自問してください。

* ファイルはすでに GitHub Releases にアップロードされていて、プロジェクト内に置かれていないか?
* asset の `browser_download_url` を正しくコピーしたか、手入力していないか?
* アップロード前にファイル名を明確な意味のあるものにしたか（publish 後の改名は困難なため）?
* alt text は画像の内容を正しく説明しているか?
* アップロード前にファイルを適切にリサイズ/圧縮したか?
* 画像の前後に説明のテキストがあるか?
* 画像にコマンドや設定が含まれる場合、対応するテキストの code block があるか?
* 動画には `controls` があり、音声付きの `autoplay` を避けているか?
* UI や内容が変更された場合、既存の asset を編集するのではなく新しい Release タグを作成したか?

## まとめ

メディア＆ファイルは技術ドキュメントをより視覚的で追いやすくしますが、プロジェクトを重くしないよう正しく管理する必要があります。

画像の基本構造:

```mdx showLineNumbers title="基本のメディア"
![内容を明確に説明する Alt text](BASE_STORAGE/<tag>/<file-name>)
```

最も重要な原則:

1. **メディアファイルをプロジェクトに commit しない** — すべての画像、動画、音声、添付ファイルは、事前に `vlib-storage` リポジトリの [GitHub Releases](https://github.com/nguynninh/vlib-storage/releases) にアップロードする必要があります。
2. **MDX では asset のリンク（`browser_download_url`）のみを使用**し、ローカルファイルのパスは使わない。
3. **アップロード前にファイル名を明確にする** — publish 後に改名すると、参照されているリンクが壊れます。
4. **常に説明的な alt text を書く** — 空欄や一般的すぎる言葉にしない。
5. **Release にアップロードする前にファイル容量を最適化する。**
6. **重要な情報を画像だけで表現しない** — 可能な限り実際のテキストも併記する。
7. **音声付きの動画を `autoplay` にしない。**
8. **メディアの内容が変わった場合は新しい Release タグを作成する** — 既存タグの asset を置き換えない。

良いドキュメントページとは、画像の数が最も多いページではなく、掲載されているすべての画像、動画、添付ファイルに**明確な存在理由があり、正しい場所に保存されている**ページです。
